线上版本：`ANL_VERSION = 1`

本文件描述当前实现。性能测量见 [PERFORMANCE.md](PERFORMANCE.md)；

## 1. 概述

AnLiu 是一个基于 UDP 的轻量传输协议，参考 [ikcp](https://github.com/skywind3000/kcp) 的实现方式：

- 只有两个文件：`anliu.h` / `anliu.c`；
- 不依赖外部库，不直接操作 socket，通过 output 回调发包、`anl_input` 收包；
- 由应用驱动时钟，调用 `anl_update` / `anl_check`。

在 ikcp 的基础上增加了以下能力：

| # | 能力 | 概要 |
|---|---|---|
| 1 | 加密与抗探测 | 数据报整体认证、conv 之后加密（12 字节标签），按传输方向派生密钥；线上没有固定明文特征 |
| 2 | 流级 FEC | GF(2⁸) Cauchy Reed-Solomon，最多 64 个数据分片与 16 个校验包；可靠流默认关闭，半可靠流默认按 RTT 与丢失证据开启 |
| 3 | 精简头部 | 公共字段提到数据报级；默认 MTU 下基础 DATA 段头 6~7 字节，分片扩展、帧号、sid 扩展与 OPEN 参数另计 |
| 4 | 多流 | sid 低 4 位与段类型合用段的第 1 字节，sid ≥ 16 时后接 varint 扩展到 25 位；sid 取本端奇偶的下一个值，一个连接内不复用；一个连接同时最多 64 个流（`ANL_MAX_STREAMS`，两端打开的与默认流合计）；流以句柄操作，两端都可随时打开和关闭，关闭通知对端并等对端确认；对端打开的流经回调自动接收并带应用 tag；流参数随第一个段携带，无握手；每流独立序号空间 |
| 5 | 半可靠帧传输 | 按帧发送，积压或超时时整帧丢弃，用 FWD 通知接收方跳过 |
| 6 | 平滑发送 | 连接级令牌桶配合 BBR 模型发送；共享带宽估计、RTT 与在途约束 |

### 1.1 非目标

以下内容不在 v1 范围内：

- 密钥交换与前向保密：使用预共享密钥（PSK），由应用负责分发和轮换（轮换上限见 3.7）；
- 重放的处理开销：包号窗口（见 4.3）挡住重放和过早的数据报，不再解析其中的段，但它们仍要先解密和认证；
- 路径 MTU 探测、连接迁移；
- 隐藏流量时序特征（随机填充只能模糊包长）；
- 完整的 QUIC/TCP 互操作或标准 BBR 实现：当前是面向实时业务的 BBRv2 / BBRv3 思路实现。

## 2. 分层结构

```
 应用层   anl_send / anl_recv                         （默认流，可靠字节流）
          anl_stream_send / anl_stream_recv           （可靠流句柄，语义同 ikcp）
          anl_stream_send_frame / anl_stream_recv_frame（半可靠流句柄）
   │
 流层     每个流独立：sn 空间、snd/rcv 队列、可靠模式、FEC 编解码
   │      所有流共享：RTT/RTO、拥塞窗口 cwnd；按优先级加权调度
   │
 包层     多个段打包进一个数据报；数据报头只写一份（conv、ts、包号 pn）
   │
 加密层   SipHash-2-4-128 认证（截断 12 字节）+ ChaCha20 加密（SIV 构造）；
   │      按方向派生密钥；可选随机填充
   │
 output 回调 → UDP
```

## 3. 加密层

### 3.1 角色与密钥派生

应用在配置里提供 32 字节 PSK，并指定本端角色 `role`：`ANL_ROLE_CLIENT`（0）或 `ANL_ROLE_SERVER`（1）。两端角色必须不同。

按**传输方向**派生两套密钥，方向 `dir` = 发送方的角色：

```
blk[dir] = ChaCha20_Block(key = PSK, nonce = "AnLiu-KDF-v1"(12B), counter = dir)   // 64 字节
k_enc[dir] = blk[dir][0..31]    // ChaCha20 密钥，32 字节
k_mac[dir] = blk[dir][32..47]   // SipHash 密钥，16 字节
k_rng[dir] = blk[dir][48..63]   // 本端内置 PRNG 的种子密钥，16 字节（仅 dir == role 时使用）
```

- 本端**发送**时使用 `dir = role` 的密钥，**验证和解密**时使用 `dir = 1 - role` 的密钥；
- 因此把 A 发出的数据报反射回 A，会因为密钥方向不匹配而认证失败。这是防反射攻击的关键；
- 两端角色配置相同时，双方无法验证对方的包；认证失败包必须静默丢弃。

每个连接用自己的配置（PSK）派生密钥；不同连接可以共用 PSK，也可以各用各的，由应用决定。服务端不需要先解密就能读出 conv（3.4），按 conv 找到连接后再用该连接的密钥验证和解密。

### 3.2 SIV 构造（发送）

设 `P` 为明文数据报（数据报头 + 各段 + 可选填充），不含 tag。

```
tag   = SipHash-2-4-128(k_mac[role], P)[0..11]         // 16 字节输出截断为 12 字节，覆盖整个 P（含 conv）
nonce = tag                                           // 12 字节 IETF nonce
off   = (tag[0] & 7) + 1                              // 1..8
convx = conv XOR tag[off..off+3]                      // conv 只做混淆，不加密
C     = P[4..] XOR ChaCha20(k_enc[role], nonce, 0)    // conv 之后的部分加密
wire  = tag || convx || C
```

只有一种模式：整包认证，conv 之后加密。conv 不是秘密：知道算法的人都能用明文 tag 还原它；混淆只是让线上不出现每包固定的 4 字节。conv 仍在认证范围内，改动它会使认证失败。tag 与 conv 共 16 字节是明文，需要的话由应用自行处理：output 回调（`int output(char *buf, int len, anl_t *w, void *user)`）拿到的是库自己的缓冲，回调返回后不再使用，可以在发送前原地改写（例如加密）这 16 字节或其他字节，但不能改变长度；接收方在自己的接收缓冲里原地还原后再调用 `anl_peek_conv` / `anl_input`。

### 3.3 接收

1. 数据报长度小于 `12 + 11` 字节，或大于配置的 `mtu`，直接丢弃（`ANL_EFORMAT`）；
2. 用 tag 去掉 conv 的混淆；用 tag 当 nonce、用 `k_enc[1 - role]` 解密 conv 之后的部分；
3. 用 `k_mac[1 - role]` 重新计算 `SipHash-2-4-128(P)[0..11]`，与 tag 做常量时间比较；
4. 比较失败时，`anl_input` 返回 `ANL_EAUTH`。**调用方不得对该包做任何回应**，这是抗主动探测的关键；
5. 认证通过后依次检查版本号/保留位（`ANL_EFORMAT`）、conv（`ANL_ECONV`）、包号（`ANL_EREPLAY`，见 4.3）、时间窗（`ANL_ESTALE`，见 4.2），任一失败即丢弃，不解析任何段。

### 3.4 服务端分发（demux）

```c
/* 不用密钥、不解密，从数据报读出 conv（去掉混淆）。未经认证，只用于找连接。
 * 返回 ANL_OK，或 ANL_EFORMAT / ANL_EINVAL。 */
int anl_peek_conv(const char *data, long size, uint32_t *conv);
```

服务端流程：每个数据报 `anl_peek_conv` → 用 conv 找到连接 → `anl_input`（用该连接的密钥认证并解密）。conv 未知时，用应用为该 conv 准备的 PSK 新建连接后再 `anl_input`；认证失败（`ANL_EAUTH`）即丢弃，不回应。

conv 未经认证：攻击者可以把任意数据报的 conv 改成另一个连接的，但这个包会在该连接的认证中失败。按 conv 先查表，垃圾数据报里 conv 未知的部分不必解密就能丢弃。

**服务端建连策略**：协议没有握手，服务端对"认证通过但 conv 未知"的数据报创建新连接，就是事实上的隐式建连。任何拿到历史抓包的人都可以重放不同 conv 的旧数据报，让服务端批量创建僵尸连接；重放包还会成为新连接第一个初始化 `peer_ts`（4.2）的包。协议层面的对策和对应用的要求：

- 服务端角色的 `idle_timeout_ms` 默认 30 s（6.6），僵尸连接会被判死，应用需调用 `anl_release` 回收；
- 应用应对"新 conv 建连"限速（例如每源 IP 每秒不超过 N 个），并限制同时存在的连接总数；
- conv 应由服务端分配并通过带外渠道告知客户端，或由客户端取随机 32 位值、服务端拒绝与现存连接冲突的值。协议不提供 conv 分配机制；
- 对端进程重启后必须使用新的 conv（见 4.2）。

### 3.5 随机填充

- `pad_max` 取值 0..255，**默认 32**；为 0 时关闭；
- 当 `pad_max > 0` 时，**不带数据的数据报**（只有 ACK / FWD / 控制段，或零段的 keepalive）追加 `N` 字节填充，`N` 在 `[1, pad_max]` 内随机，且不超过 MTU 剩余空间；带 DATA 或 PARITY 的数据报不填充：它们的长度本来就随媒体帧变化，填充只增加开销（平均约 14 字节/包，160 字节的音频帧约 9%）；
- 填充的最后 1 字节是 `N` 本身，其余字节随机；
- 数据报头 flags 中的 `PAD` 位表示本包带填充。

随机源：`anl_config.rng` 回调（`void rng(void *user, uint8_t *buf, size_t n)`）可选。未提供时使用内置 PRNG：`ChaCha20(k_rng[role], nonce = 对象地址 ⊕ conv 在 anl_create 时确定, counter 递增)`，首次 `anl_update` 时再把 `current` 混入 nonce。种子必须在 `anl_create` 就可用，因为 `flush_on_send`（6.5）可能在第一次 `anl_update` 之前就需要填充。填充内容位于加密区内，其可预测性不影响机密性；只有 `N` 的分布影响抗流量分析的效果。

默认开启填充是因为 ACK-only 数据报的长度否则固定为 `23 + 11` 字节左右，是明显的协议指纹。

### 3.6 包号窗口与数据报时间窗

见 4.3 和 4.2。两者都是加密层之上的完整性补充：认证只能证明"这个包是持有 PSK 的一方发的"，不能证明"这个包不是旧包"。包号窗口挡住重放和过早的数据报；时间窗挡住滞留过久的数据报和倒退的时钟。

### 3.7 安全性说明

本协议的密码构造是 SipHash-2-4-128（截断）+ ChaCha20 拼成的 SIV，没有现成的安全证明和参考实现；12 字节标签是为了省开销做的刻意取舍。安全目标显式列出如下，使用者据此判断是否满足场景：

- **伪造**：每次尝试成功概率 2^-96；
- **机密性**：SIV 是确定性加密，相同的 P 得到相同的密文。tag 兼作 nonce，nonce 碰撞会导致 ChaCha20 密钥流重用。碰撞服从生日界：N 个数据报的碰撞概率约 `N^2 / 2^97`。**单个 PSK 的所有连接、两个方向合计不超过 2^40 个数据报**（约 1.1 万亿，碰撞概率 < 2^-17），超过前应轮换 PSK；
- **反射**：由方向密钥防止；
- **重放**：每个数据报带本方向的包号，接收端记住最近 4096 个（4.3），重复或更早的在认证后直接丢弃，不解析任何段；攻击者仍能让接收端为重放包付出解密和认证的开销；
- **流量分析**：不防；随机填充只模糊包长分布；
- **密钥分离**：同一 PSK 的所有连接共用密钥，任何持有 PSK 的一方都可以伪造任意 conv 的数据报。PSK 的信任边界是"同一组互信端点"；
- **未认证包的处理代价**：SIV 必须先解密整个 P 才能计算 tag，垃圾数据报也有解密和认证成本。历史加解密测量见 PERFORMANCE.md。
- 版本号位于加密区内，密码套件升级无法通过版本号协商，只能靠更换端口或 PSK 实现（见第 4 节）。
- **conv 可见**：conv 只做混淆，算法公开，旁观者可以还原 conv，跨数据报、跨 IP/端口变化关联同一连接。需要隐藏时由应用在库外处理前 16 字节（3.2）。

## 4. 数据报格式

字节序统一使用小端，与 ikcp 一致。varint 使用 LEB128（小端，每字节 7 位，最高位为续标志），**最多 3 字节**，超出视为 `ANL_EFORMAT`。

```
  0             12       16     17       19       23
  +-------------+--------+------+--------+--------+-----------------------+-------------+
  | tag (12)    | conv(4)| flg  | ts (2) | pn (4) |  段 1 | 段 2 | ...     | [填充 N 字节] |
  +-------------+--------+------+--------+--------+-----------------------+-------------+
   明文           混淆     └──────────────────────── 加密区（一直加密到包尾）─────────────┘
                  └──────────────────────────────── 认证范围（P）──────────────────────────┘
```

| 字段 | 大小 | 说明 |
|---|---|---|
| tag | 12 | SipHash-2-4-128 标签的前 12 字节，同时作为 nonce |
| conv | 4 | 连接号，非零；线上为 conv XOR tag[off..off+3]，off = (tag[0] & 7) + 1（3.2） |
| flg | 1 | bit7-6：版本号（当前为 1）；bit0：PAD；其余位保留，必须为 0 |
| ts | 2 | 发送方时钟（毫秒）的低 16 位，供对端在 ACK 中回显，并用于时间窗检查；接收端扩展回 32 位（4.2） |
| pn | 4 | 本方向的数据报包号，从 0 起每个数据报加一；接收端据此丢弃重放（4.3） |

**数据报级固定开销为 23 字节**，其中 12 字节用于认证和 nonce，4 字节是包号。

- 收到版本号未知或保留位不为 0 的包，直接丢弃；
- 允许 0 个段的数据报（只有头部和可选填充），用作 keepalive（见 6.6）；
- 默认 MTU 为 1400，与 ikcp 相同。

### 4.1 版本号的局限

版本号在加密区内，只有解密成功后才能读到。因此它只能用于同一密码套件下的格式演进；更换密码套件属于不兼容升级，需要新的端口或 PSK。

### 4.2 时间窗检查

重放由包号窗口（4.3）挡住。时间窗是它之上的第二道检查，针对的是包号窗口放过的两种情况：在网络中滞留过久、仍落在最近 4096 个包号之内的数据报，以及对端时钟倒退（例如进程重启后沿用 conv）。接收端在连接级做一次基于 ts 的检查：

- 连接记录对端最近的 ts：`peer_ts`（用有符号 32 位差值比较，允许回绕）；
- **16 位 ts 的扩展**：线上只有发送方时钟的低 16 位（约 65.5 s 一圈）。接收端以"对端此刻应有的时钟"为参考：`ref = peer_ts + (本地 current − 记下 peer_ts 时的本地 current)`，取 `ts32 = ref + sext16(ts16 − ref)`。参考随本地时间前进，连接静默超过半圈（32.7 s）后到达的新数据报也不会被当作旧包；两端时钟速率相同（都是毫秒单调时钟），漂移远小于半圈；
- 认证通过后，若 `diff(ts32, peer_ts) < -ts_window`，丢弃该数据报，`anl_input` 返回 `ANL_ESTALE`；否则 `peer_ts = max(peer_ts, ts32)`，但 `ts32` 超前 `ref` 超过 1 s（`TS_AHEAD_MAX`）时只取 `ref`。录下后 33..65 s 重放的数据报，扩展结果落在"未来"，若照单全收会把 `peer_ts` 推前最多 32 s，其后所有正常数据报都被判为过期，一次重放就能让连接停顿。正常数据报只会超前 `ref` 几毫秒（`current` 是上一次 update 的时间，两端时钟速率也略有差别），必须照收：一律截到 `ref` 时 `peer_ts` 只会越来越落后于对端的时钟，CTRL_ECHO 回送的正是它，只收不发的一端因此量到的 RTT 偏长（实网 101 ms 量成 116..122 ms），到阈值后 7.5 节的"补不回来的缺口立即跳过"把重传还来得及补的缺口也跳过（2026-10-08）；
- `ts_window = cfg.ts_window_ms`，默认 1000，**固定值，不与 RTO 挂钩**，上限 30000（远小于 16 位 ts 的半圈）。时间窗防的是在网络中滞留过久的旧数据报，与重传无关（重传总是放在带新 ts 的新数据报里）；若与 RTO 挂钩，ikcp 的 RTO 上限 60 s 会让窗口膨胀到 240 s，每流速率上限随之降到约 136 分片/秒，保护形同虚设；
- 第一个通过认证的数据报直接初始化 `peer_ts`。

由此带来的约束（需要在使用文档中写明）：

- 对端的 `current` 必须是单调时钟。若它向后跳超过 ts_window，其数据报会被丢弃直到时钟追上；
- 24 位 sn 的歧义：时间窗内的数据报同时在最近 4096 个包号之内，一个数据报最多几十个分片，远不到 2²³，sn 不会歧义；
- **对端进程重启后必须使用新的 conv**。重启后包号从 0 开始，落在接收端窗口之下而被丢弃（4.3，本方向发出约 2³² − 2²⁴ 个数据报之前都是如此）；`current` 通常也从另一个基准重新计时，ts 大幅倒退，同 conv 的数据报会被永久判为 ESTALE。协议不做"连续多个 stale 则重置 peer_ts"之类的自愈：那会给重放攻击开后门。同 conv 重连在 ikcp 里同样是错误用法（sn 空间从 0 重置），这里只是让失败更早、更明确。

### 4.3 包号与重放窗口

每个方向独立维护 32 位包号 `pn`，从 0 开始，每个数据报加一：DATA、ACK、控制段、PARITY、keepalive 都算，重传的数据放在带新包号的新数据报里，流内 sn 不变。包号在加密区内，线上不可见，由 tag 认证。

接收端记录认证过的最大包号 `rx_pn_max` 和它之下 4096 个包号的位图（512 字节）：

- 包号比最大值大 1..2²⁴（`PN_AHEAD`）算领先，其余都算落后；
- 认证、版本和 conv 检查通过后，落后的包号已置位或比最大值小 4096 以上的数据报丢弃，`anl_input` 返回 `ANL_EREPLAY`，统计 `rx_replay`；不解析其中任何段，也不更新 `peer_ts`；
- 其余数据报再做时间窗检查（4.2），通过后才置位：更大的包号把窗口上移，让出的位置清零；被时间窗丢弃的数据报不记包号；
- 窗口内未见过的包号照常接收，乱序不受影响。窗口按包数计：1 Gbps、1400 字节时约 46 ms，媒体码率下几十秒。超出窗口的乱序在这些场景下不存在；
- 包号按 32 位模计算，回绕后窗口继续工作。领先只认 2²⁴ 以内：连续丢失 1600 多万个数据报的路径早已判死。若按半个模（2³¹）判断领先，一个方向发出 2³¹ 个数据报之后，录下的最早那批数据报重放时会被当作领先接收，并把窗口一下推到前面，其后的正常数据报全部判为重放；重启后从 0 开始的包号也不再落在窗口之下。现在只有发出约 2³² − 2²⁴ 个数据报之后（10 万包/秒持续约 12 小时），那时录下的最早旧包才可能被当作领先，仍由时间窗和 sn 兜底；
- 重放只能阻止重复处理，不能免去解密和认证的开销（3.7）。

## 5. 段格式

每个段以 1 字节开头（sid ≥ 16 时后接 1..3 字节扩展，下称 sid_hdr）：

```
 b0: bit 7 6 | 5 | 4 | 3 2 1 0      [sid_hi: varint，仅当 F = 1]
       type  | 0 | F | sid[3:0]             sid >> 4
```

- `sid = sid_hi << 4 | sid[3:0]`，范围 0..2²⁵−1（`ANL_MAX_SID`）。sid < 16 时 F = 0，只有 1 字节；否则 F = 1，后接 sid_hi 的 varint（16..2047 为 1 字节，更大为 2..3 字节）。默认流和每端最先打开的 7 个流都在 1 字节内；
- **一个 sid 只有一种编码**：F = 1 而 sid_hi 为 0、或 varint 不是最短编码时，按 `ANL_EFORMAT` 丢弃整个数据报；
- bit 5 保留，必须为 0，否则按 `ANL_EFORMAT` 丢弃整个数据报；
- 解密后最多读 4 字节即可得到流 ID，之后的字段按相对位置解析；

| type | 名称 | 用途 |
|---|---|---|
| 0 | DATA | 数据分片 |
| 1 | ACK | 确认，兼作窗口通告和窗口探测 |
| 2 | FWD | 半可靠流通知接收方跳过 |
| 3 | CTRL | 扩展控制，2 字节公共段头之后的第 1 字节为子类型 |

### 5.1 序号编码

- 线上的 sn 和 una（DATA、ACK、FWD、PARITY 的 base）都是 **24 位**，内部扩展为 32 位：`sn32 = ref32 + sext24(sn24 − ref32)`；
- 接收方的参考值 ref 取 `rcv_nxt`，发送方取 `snd_una`；
- 要求窗口远小于 2²³；`snd_wnd` 与 `rcv_wnd` 上限为 `ANL_MAX_WND` = 32768，这是 ACK 的 wnd 与流参数的 rcv_wnd（均为 u16）的限制，而不是序号空间的限制。32768 个约 1366 字节的分片约 45 MB，RTT 300 ms 时可支撑约 150 MB/s；
- 窗口限制只保证在途数据不歧义，不保证旧包不被当作新包，后者由 4.3 的包号窗口负责（滞留过久的数据报由 4.2 的时间窗挡住）。

### 5.2 DATA

```
 sid_hdr : 1..4 字节，type=00
 flags   : OPEN(1) | HAS_FRAME(1) | KEY(1) | frg(5)
 [frg_ext]: varint，仅当 frg5 == 31 时出现，实际 frg = 31 + frg_ext
 sn      : u24
 [frame] : u16，仅当 HAS_FRAME 时出现，为 frame_no 的低 16 位
 [open]  : 5 字节流参数，仅当 OPEN 时出现，见下
 len     : varint
 payload
```

**流参数（open body，5 字节）**，DATA / STREAM_OPEN 共用：

```
 ob      : u8     bit0 = SEMI（半可靠流），bit1 = STREAM（字节流模式，仅可靠流），bit7-2 保留（发 0，收到时忽略）
 rcv_wnd : u16    打开方的接收窗口，两端相同
 tag     : u16    应用定义的流用途
```

**分片大小**：连接 mss = MTU − 23 − 12（23 为数据报固定开销 `ANL_OVERHEAD`：明文头 11 字节加 12 字节 tag；12 为 DATA 头部最大值：sid 1、flags 1、frg_ext 3、sn 3、frame 2、len 2，不含流参数）；sid ≥ 16 的流 mss 再少 sid 扩展的字节数。对端尚未应答时切出的分片，载荷上限为 mss − 5，重传时仍可能携带流参数而不超过 MTU；收到对端任何段之后切出的分片使用完整 mss（peer_opened 只会从 0 变 1，之后切出的分片不会再带流参数）。只让少量早期分片承担这 5 字节，而不是整条连接一直少 5 字节 mss。

- **frg**：分片倒计数，最后一片为 0，第一片为 n-1；解析时要求 `frg < ANL_MAX_WND`，过大的扩展值返回 `ANL_EFORMAT`。
- **len**：payload 长度，varint。
- **OPEN**：打开方在**收到对端该流的任何段之前**，发出的每个 DATA 都带流参数（多 5 字节）；收到对端的任何非 RST 段后清除。接收方靠它在数据到达时直接建流（见 6.1），不需要单独的握手。
- **HAS_FRAME / KEY**：只出现在半可靠流中每一帧的**首个分片**上。HAS_FRAME 同时是帧起点标记，接收方靠它来跳帧。
- **模式校验**：可靠流收到带 HAS_FRAME 的 DATA、或收到 FWD，说明对端把该 sid 当作半可靠流；本端向对端发 RST 并按"对端已释放"处理该流（见 6.1）。默认流（sid 0）例外：只丢弃这个违规段，默认流照常工作。
- **头部大小**：
  - 可靠流（不含 frg_ext）：`1 + 1 + 3 + (1~2)` = **6~7 字节**；sid ≥ 16 时再加 sid 扩展；对端尚未应答时再加 5 字节；
  - 半可靠流的帧首片：再加 2 字节。

### 5.3 ACK

```
 sid_hdr : 1..4 字节，type=01
 flags   : WASK(1) | FRESH(1) | 保留(6)
 una     : u24     接收方仍需要的第一个 sn（半可靠流可跳过缺口，见 7.5）
 wnd     : u16     接收方剩余窗口
 ts_echo : u16     回显最近一个带有本流 DATA 的数据报的 ts（低 16 位）
 n       : varint  后面的区间个数
 gap[i]  : varint  区间起点 - 上一个区间的终点（第一个区间相对 una）；第一个可以为 0，其余 ≥ 1
 len[i]  : varint  区间长度，≥ 1；区间 [起点, 起点 + len) 内的分片都已收到
```

**区间确认（SACK）**：区间直接由 rcv_buf（una 之上、乱序到达的分片）生成，按升序列出：

- 每个分片记录自己被报告的次数；一个区间只要其中有分片被报告少于 **3 次**（`SACK_REPEAT`）就列入本次 ACK，所以一个分片会出现在至少 3 个 ACK 中，单个 ACK 丢失不再引起多余重传或队头停滞；
- 收到已有的分片（发送端重传了它，说明发送端可能不知道它已送达）时，把它的报告次数清零，重新报告；
- 一个 ACK 段放不下时拆成多个 ACK 段，每段都带完整的 una / wnd / ts_echo；
- 编码：连续收到的分片只占一个区间，连续区间只需一个 gap/len 对；从 una 开始的连续确认直接通过 una 表达；
- 接收端检查：除第一个区间外 gap 为 0、len 为 0、区间总跨度超过 `ANL_MAX_WND` 的 ACK 视为格式错误；发送端忽略终点超过 snd_nxt 的区间；
- 第一个区间的 gap 为 0 出现在接收队列满（`nrcv_que ≥ rcv_wnd`）时：rcv_nxt 处的分片已收到但不能移入队列，una 停在它上面，区间从 una 开始。

**ts_echo**：发送端用自己的时钟还原为 `current − (u16)(current − ts_echo)`，即低 16 位相同的最近时刻；RTT 不超过 65.5 s 时无歧义（RTT 样本本来就限制在 RTO_MAX 60 s 以内）。同一数据报的多个流各自回显不同的 ts（音频与视频最近一次到达的数据报不同）。

**标志位**：

- `FRESH`：自上一个 ACK 以来收到过本流的数据，ts_echo 是新的，可以作为 RTT 样本。只有 FRESH 的 ACK 参与 RTT 计算和 RACK；窗口探测的应答、FWD 触发的 ACK 不带 FRESH；
- 旧格式中每个 sn 只确认一次，而区间会在多个 ACK 中重复出现，所以发送端对已经删除的分片再次收到确认是正常的，直接忽略。

**补发 ACK**：带新信息（FRESH）的 ACK 发出后，若一个 update interval 内没有别的 ACK 发出，再补发一次。按帧节奏发送的流在帧间不产生 ACK，一帧最后的 ACK 丢失时，其分片只能等发送端 RTO；补发不带 FRESH，不产生 RTT 或 RACK 样本，只让确认早到。

- **RTT 计算**：`rtt = now - ts_echo`。ts 标识的是某一次具体的发送，所以不存在 Karn 歧义。RTT/RTO 在连接级统一维护。**一个收到的数据报最多产生一个 RTT 样本**：取其中所有 ACK 段里最新的 ts_echo，避免多个流回显同一个 ts 时重复采样、压低 rttval。样本 `< 0` 或 `> 60 s` 视为无效并忽略（认证通过的数据报里 ts_echo 也可能因实现错误或时钟问题而离谱，直接代入 srtt 会导致整数溢出）。
- **窗口探测**：
  - 对端窗口为 0 且本流仍有待发/未确认数据时，发送 `WASK=1` 的 ACK，替代 ikcp 的 WASK；首次等待连接当前 RTO，后续重试先保证间隔不小于当前 RTO，再 ×1.5，上限 60 s。没有 RTT 样本时沿用连接初始 RTO。恢复正窗口后清除探测退避；探测不允许绕过真实的零窗口发送新 DATA；
  - 接收端读走数据后的窗口通告可能丢失；即使发送端没有未确认 DATA，仍需 WASK 来获取恢复后的窗口。
  - 对端回一个 `n=0` 的 ACK，替代 ikcp 的 WINS。
- **触发条件**：收到本流的 DATA（半可靠流包括落在接收窗口之外、存不下的 DATA）、收到 FWD（无论是否改变了 rcv_nxt）、接收端因 rcv_deadline 跳帧之后，都必须为该流排一个 ACK。后三条是 FWD 能收敛的前提（见 7.4）。
- **发出时机**：`anl_input` 处理完一个带 DATA 的数据报后，若自上次发出 ACK 起已累计收到 **2 个**带 DATA 的数据报，或该数据报带 FWD / WASK，则在 `anl_input` 返回前立即发出一个只含 ACK/CTRL 的数据报；否则等下一次 flush。这与 TCP 延迟确认的"每两个段确认一次"一致，ACK 数量约为数据报的一半。ACK-only 数据报不消耗 pacing 令牌（6.7），且 `anl_input` 内会同步调用 output。output 回调不能调用任何 `anl_*` 函数（重入约束见 anliu.h 文件头）。

### 5.4 FWD（仅半可靠流）

```
 sid_hdr : 1..4 字节，type=10
 new_una : u24    所有小于 new_una 的 sn 都已被发送方放弃
```

共 4 字节（sid ≥ 16 时加 sid 扩展）。new_una 由本次放弃的、已分配序号的分片确定：越过其中最大的 sn，但不越过后续未放弃的分片。它不要求落在帧首，也不等于发送缓存中第一个存活帧或分片的 sn；与 `snd_una` 是两个不同的量，详细规则见 7.3。

### 5.5 CTRL

```
 sid_hdr : 1..4 字节，type=11
 subtype : u8
 len     : varint  body 的字节数
 body[len]
```

| subtype | 名称 | body | 说明 |
|---|---|---|---|
| 0x00 | 保留 | — | — |
| 0x01 | PARITY | 见 8.3 | FEC 校验段 |
| 0x02 | STREAM_OPEN | 5 字节流参数（5.2） | 单向通告：打开方尚未收到对端任何段时，按退避周期发送，让对端在没有数据的情况下也能建流；对端回一个普通 ACK（n=0）即可，见 6.1 |
| 0x03 | RST | 空 | 本端没有这个 sid 的流（已关闭、拒绝或从未有过）：对端收到后释放该流，应用读写返回 `ANL_ECLOSED`；也是对 CLOSE 的确认。对 RST 不回应，见 6.1 |
| 0x04 | REPORT | 8 个 u16：`jitter qdelay_avg qdelay_max frame_delay_avg frame_delay_max frames frames_skipped fec_recovered`，再加 `rx_bytes(u32)` 和 `sender_ts(u16)` | 接收端的时延报告（6.9），毫秒；`frames_skipped`、`fec_recovered` 是累计值（模 65536），`rx_bytes` 是累计值（模 2^32）。固定 22 字节；`sender_ts` 回显接收端最近看到的发送端数据报时间戳，用于排除变速前生成的快照。短于 22 字节的 REPORT 与其它过短的控制段一样跳过，同一数据报里其后的段照常处理；开发阶段不读旧格式（16/20 字节），格式定型时再递增 `ANL_VERSION`（现在仍为 1）。不确认、不重传，下一次报告会覆盖它 |
| 0x05 | RCV_SKIP | `retired_una(u32)` | 接收端本地期限跳过的前缀终点。半可靠发送端回收该点之前仍未确认的分片，不计为实际交付；在相关 ACK 之前发送，见 7.5 |
| 0x06 | ECHO | `ts_echo(u16) hold(u8)` | 对端最新数据报头的 ts 与它在本端已停留的毫秒数。只收数据的一端只发 ACK，ACK 不被确认，它因此没有 RTT 样本；发送端在最近收到过对端 ACK、且 ECHO_MS（100 ms）内本端没有发出带回显的 ACK 时，每 100 ms 最多附带一个（约 5 字节，相当于 SRT 的 ACKACK）。只在收到 ACK 后回送，两个都只发 ECHO 的端点不会互相回送下去。接收方得到 `RTT = now − ts_echo − hold`，取 10 s 窗口最小值单独保存（echo_rtt），不进入 srtt / rto / min_rtt：这些决定本端的发送节奏，接收端的报告周期也跟随 srtt，媒体参数是按接收端没有 RTT 样本时调好的。用途见 7.5 |
| 0x07 | CLOSE | 空 | 本端已关闭这个流：对端释放它（已按序到达的数据仍可读）并回 RST；本端按退避重发直到收到 RST，见 6.1 |
| 其他 | 保留 | — | 按 len 跳过 |

- 收到未知 subtype 时，按 len 跳过这个段，继续解析后面的段。这样以后新增控制类型时，旧版本的实现也能兼容。

## 6. 流层

### 6.1 流管理与关闭

**默认流 sid 0** 随连接创建，可靠字节流，任何一端都不能关闭；`anl_send / anl_recv / anl_peeksize / anl_waitsnd` 作用于它。它的重传和新数据严格优先，发送即 flush；窗口由 `default_snd_wnd / default_rcv_wnd` 设置，两端默认均为 4096，不通过 OPEN 交换。

**其他流** 由 `anl_stream_open` 分配句柄与 sid：客户端偶数，从 2 开始；服务端奇数，从 1 开始。每次取本端奇偶的**下一个 sid**，一个连接内不复用：迟到的段只可能属于一条已经消失的流，不会被当成新流的段。sid 范围 0..2²⁵−1，每端 2²⁴ 次打开后用尽，`anl_stream_open` 返回 `ANL_ENOSID`，应用另建连接；每端最先打开的 7 个流 sid 段头占 1 字节，之后 2 字节（sid < 2048），再往后 3 字节。`ANL_EBUSY` 只有一种含义：连接上已有 `ANL_MAX_STREAMS`（64）个流（两端打开的与默认流合计，本端关闭后尚未得到对端确认的也计入），等某个流关闭并确认或被重置、释放位置后重试。

打开方决定 `mode / stream / tag / rcv_wnd`，通过 5 字节 OPEN body 通告，两端采用相同值；其余选项是本端配置，可不同。尚未收到该流对端的任何段时，每个 DATA 携带 OPEN body；另发 STREAM_OPEN，使无业务数据时对端也能建流。无需等待握手即可发送数据。STREAM_OPEN 首次重试无 RTT 时用 200 ms，之后 ×2，上限 5 s；不计入 dead_link。

"收到对端任何段"：ACK、FWD、PARITY、REPORT 都算。sid 不复用，一条已经消失的流迟到的 ACK 不可能被当作现在某条流的应答。

未知 sid 的 OPEN 数据由 `anl_set_accept` 注册的回调接收；未注册时按默认参数接收。回调的 opt 预填对端的四个公共参数，不能修改这四项，其余本端选项可改；返回负数拒绝并回 RST。本端已有 64 个流时，对端新开的流同样回 RST；需要限制对端流数时由 accept 回调决定。

**对端流的接收内存由对端决定**。`rcv_wnd` 是打开方的参数（上限 `ANL_MAX_WND` = 32768），接收方不能调小，只能拒绝整条流。对端只要在 rcv_nxt 处留一个洞，就能让接收方为这条流留住整整一个窗口的乱序分片，与应用是否读取无关：每个分片一个约 144 字节的段结构加载荷，每个洞再加一个约 48 字节的区间记录。默认 MTU 下满载荷分片每流约 49 MB，一个连接最多 63 条对端流，合计约 3 GB；1 字节的小分片每流约 6 MB，线上只有约 7 字节一段，结构开销放大约 25 倍。这些都有界，但对服务端来说偏大：对端不可信时，应在 accept 回调里按 `opt->rcv_wnd` 和 `mode` 拒绝超出预算的流（例如可靠流 4096、半可靠流 512 的默认值），并限制对端流数。未注册回调时全部接受，不做此检查。应用用 `tag`、用户指针或 `anl_readable` 识别业务流。

句柄从 open 或 accept 起有效，直到应用 close 或释放连接。`anl_readable` 返回有可读数据或已经结束（对端关闭、被重置）的句柄，返回总数，即使 out 容量不足也报告完整数量。

**关闭通知对端，对端确认后才让出位置**：

- `anl_stream_close` 立即释放本端的发送/接收缓冲、FEC 状态和 sid 表中的位置，句柄失效；待发、在途和未读的数据全部丢弃。需要数据送达的可靠流，应等 `anl_stream_waitsnd` 为 0 再关闭。没有半关闭；
- 同时本端记下这个 sid（"关闭中"：sid、下次重发时刻、退避间隔和已发次数），并发 **CLOSE**（CTRL 0x07，无 body）；没有回应就重发，间隔与 STREAM_OPEN 相同：首次用 RTO，无 RTT 时 200 ms，之后 ×2，上限 5 s；不计入 dead_link，连接不会因此判死。收到这个 sid 的 RST 后删除记录。连发 dead_link 次（默认 20 次，约 80 s）仍无回应就放弃记录：对端可能已经消失（它可能一直留着那一端），而客户端默认没有空闲超时，否则会无限期地每 5 s 发一次。连接死亡时不再发送，释放连接时一并丢弃；
- 关闭中的记录计入本端 `anl_stream_open` 的流数上限，不计入接受对端新流的上限。理由：对端收到 CLOSE 之前仍占着这个流的位置，本端此时再开新流，可能到达一个已满的对端而被 RST；接受对端的新流时，对端自己的计数已经包含它仍占着的流。由此，任何一个流只要还在对端的流表中，就一定还在关闭方的计数中，关闭不会造成两端计数不一致。两端同时开新流导致的超限仍可能发生（见上文"本端已有 64 个流"），与关闭无关；
- 对端收到 CLOSE：
  - 流还在：释放它（同上，但已按序到达、在接收队列中的数据保留，应用仍可读完，之后读写返回 `ANL_ECLOSED`；半可靠流队尾不完整的帧丢弃），回 RST。关闭方等可靠流 `waitsnd` 为 0 再关闭时，对端应用因此能读到全部数据；
  - 没有这个流：本端也关闭了（双方同时关闭，对方的 CLOSE 就是确认，删除本端的关闭中记录）、早已释放，或从未见过（关闭方在对端收到任何段之前就关闭，此时把 sid 记入保留期，迟到的 DATA 得到 RST，不会再建流）；都回无状态 RST。每次收到 CLOSE 都回，因为上一次的 RST 可能丢失；
- 对端只是被关闭方通知，它那一端的句柄仍由它的应用 close，此时不再发 CLOSE；
- 关闭中的记录与保留期记录（见下）共用一张 128 项（`2 × ANL_MAX_STREAMS`）的定长表（sid、时刻、退避间隔、已发次数、是否关闭中），顺序查找。表满时先挤掉最早到期的保留期记录（它的保留期提前结束），没有保留期记录时放弃已重发次数最多的关闭中记录（之后只是不再计入本端的上限；对端可能一直留着那一端）；
- 未知 sid 的 ACK、FWD 及 CLOSE 以外的 CTRL 静默丢弃。对 RST 不回应，防止循环；
- 拒绝接收（accept 回调返回负数、本端已满 64 个流）、保留期内的 sid 再次带 OPEN、模式不一致、可靠流收到 FWD 或带帧号的 DATA 等违规，都回 RST 并在本端释放该流；被重置的流句柄保留到应用 close，接收队列中的数据丢弃；应用 close 被重置的流时不再发 CLOSE；
- 默认流（sid 0）不会被对端结束：它的 CLOSE、RST 不处理；带帧号的 DATA、FWD、模式或字节流标志不符的 OPEN 这些对其他流会触发重置的违规段，在默认流上只丢弃这一段，不回 RST，默认流和已收到的字节流不受影响。否则对端一个数据报就能让默认流永久结束，而连接看起来仍然存活；
- 对端在已释放的 sid 上发来的 DATA（不论是否带 OPEN）仍得到无状态 RST，例如 CLOSE 到达之前对端已发出的数据；
- 线上格式与加包号之前的版本不兼容（第 4 节），两端须同时升级；版本号仍为 1；
- 关闭不计入 dead_link。

流表是 64 项的定长数组（无序），查找时顺序扫描比对 sid；另有一条所有流结构的链表（含被重置、句柄仍由应用持有的流）。有控制输出待发的流做标记，即时 flush 只处理有标记的流，定时 flush 遍历全部。无状态 RST 每次 flush 最多 128 个，更多的等对端下一个段再回。

**保留期**（相当于 TCP 的 TIME_WAIT）。**对端打开的**流在本端消失（本端关闭并收到对端的 RST、对端 CLOSE、RST、重置、拒绝）时，它的 sid 进入保留期：2 s（`SID_HOLD_MS`），`ts_window_ms` 加 1 s 更长时取后者（默认时间窗 1 s 时正好 2 s）。保留期要盖住时间窗：数据报在对端持续发送时最多滞留约一个时间窗而不被丢弃，时间窗调大（最大 30 s）而保留期不变，就会让更多迟到的数据报落在保留期之后；之后每收到这个 sid 的 CLOSE 或 RST 都重新计时。保留期内这个 sid 带着流参数再来（消失的那条流迟到的首个数据报）回 RST，不建流。本端关闭对端打开的流时，它先是关闭中记录，对端的 RST 到达后转为保留期记录。本端自己打开的流不需要保留期：它的 sid 不会再分配，迟到的 RST、CLOSE、ACK 都找不到流，各按"没有这个流"处理，本端不记任何东西。

还挡不住的情况：对端已消失的流带流参数的首个数据报在保留期之后才到，本端会建出一条对端早已没有的流（应用从 accept 回调得到它，直到本端关闭它、对端回 RST）；不带流参数的迟到 DATA 任何时候都只换来无状态 RST。对端持续发送时时间窗会挡住前者；对端静默期间时间窗的参考 `peer_ts` 不前进，滞留更久的数据报也能通过，所以它要求数据报滞留超过保留期、且恰在对端静默时到达，媒体场景下这样的数据报早已超过 max_age。

### 6.2 每流状态

各流独立保存 `snd_queue / snd_buf / rcv_buf / rcv_queue`、`snd_una / snd_nxt / rcv_nxt / rmt_wnd`，以及打开/重置状态、ACK/FWD 计时、帧号与依赖状态、FEC 编解码缓存和时延测量。首次发送才分配 sn；内存中序号为 32 位，线上 sn/una 为 24 位。

分片保存最后发送时刻、RTO 与发送次数、RACK 标记及交付采样快照；接收乱序分片保存 SACK 重复次数。各流序号空间独立，连接共享 RTT、RTO、RACK 送达证据、BBR 与 pacing。

### 6.3 RTT、窗口与丢包恢复

第一个 RTT 样本前 RTO 为 600 ms。之后：

```
srtt   = 首样本 RTT，后续按 1/8 平滑
rttval = 首样本 RTT / 2，后续按 1/4 平滑偏差
rto    = srtt + max(2 × interval, 4 × rttval, srtt / 4)
```

两个更新间隔的下限覆盖对端 ACK 等待 flush 的延迟（最多一个间隔）和丢失 ACK 的补发（再晚一个间隔，5.3）：只留一个间隔时，低 RTT 下 RTO 与这两者赛跑，20 ms RTT 无丢包时音频每秒一次伪超时，5..15% 丢包时约三分之一的超时重传到达时对端已有该分片。RTO 限制在 30..60000 ms；分片超时后按 ×1.5 退避。分片的超时时刻另加它排在本端瓶颈积压之后的时间：所有发出的线上字节按 max(带宽估计, burst_bw) 排空，得到发送时刻仍在前面的积压，换算为时间后最多一个 srtt；容量不足时不加。关键帧及其校验包以高于瓶颈的速率发出，会推迟后续分片，按平滑 RTT 得出的 RTO 会对对端已收到的分片超时重传。每个输入数据报最多取一个 RTT 样本，来自 FRESH ACK 中最新的 ts_echo；负值与超过 60 s 的样本忽略。 收包间断超过当前 RTO 后进入回显恢复阶段：没有新确认发送缓冲中的分片、且回显年龄超过当前 RTO 的 ACK 不更新 RTT，避免积压的旧 ACK 重新放大计时器。收到年龄在当前 RTO 内的有效时延样本后退出恢复阶段。持续到达的普通 ACK 及窗口内的媒体回显仍可反映排队；真正新确认的数据仍可学习超过当前 RTO 的时延。

新数据受连接 cwnd、每流 `min(snd_wnd, rmt_wnd)` 与 pacing 共同约束。cwnd 限制新分片进入 snd_buf，重传不受 cwnd 预算限制，仍受 pacing 限速。FEC 校验段不进入待确认 inflight，但占本次 flush 的新数据预算。cwnd 上限 `ANL_MAX_WND`（32768），普通初始值 16，`start_rate` 可扩大初始窗口。

**RACK**：连接保存所有流 FRESH ACK 的最新发送时刻；每流另保存最新送达序号。比未确认分片晚发的数据已送达、且等待时间达到 `rack_rtt + reo_wnd` 时，标记丢失并重传。同一毫秒发送的分片用本流序号区分。RACK 判定在 flush（周期 flush，或收包、发送触发的 flush）中进行，不单独唤醒。

可靠流同一分片的重传再被 RACK 判丢时，与 RTO 一样把它的 rto ×1.5 退避；下一次重传至少间隔 min(rto, 2^xmit ms)，即 4、8、16 … ms，之后受这个退避后的 rto 限制。原先间隔上限固定为未退避的 rto（且不超过 256 ms）：路径反复丢同一个分片、其余数据照常送达时（实网中路径按大小丢包的时段），RACK 每个 rto 判一次丢失，约 20 个往返就用满 dead_link。100 ms 路径上 2.7 s 判死，而对端一直在确认别的数据。现在用满 dead_link 要几分钟，与整条路径中断时只靠 RTO 退避的时间相当；第一次快速重传和半可靠流的期限不变，前 7 次左右的间隔也不变（2^xmit 小于 rto）。代价：分片连续丢失多次后，路径恢复时要等一个已退避的间隔（仿真中 10 s 的大包黑洞恢复后约 7 s 送达）。

乱序窗口基准为 `min_rtt / 16`，至少 1 ms、至多 srtt。可靠流按 Eifel 检测到的伪 RACK 重传扩展系数，每个 RTT 最多一次，连续干净轮次后逐步缩小；半可靠流保持最小窗口。ACK 回显早于最后重传时刻说明确认来自原包，不能把这次重传当作已证实丢失。RTO 的伪重传不扩大乱序窗口。半可靠主动丢帧本身不等同于拥塞丢包。

**大窗口的开销**：每个 ACK 的处理开销不随在途分片数增长。每个分片除 snd_buf（sn 顺序）外还挂在一条按最近发送时间排序的链表上，RACK 沿它遍历，遇到第一个发送时间晚于对端已收到的最新数据报的分片即停止；每流维护"已判丢失、尚未重传"的计数，在途量不必逐个统计；每流记录最早 RTO 到期时间的下界，无丢失也无到期时不遍历重传；接收端把 rcv_buf 另按连续区间组织，SACK 区间、重复报告计数与新分片的插入都在区间上完成，开销随空洞数增长。`bench/wndcost.c` 可测量不同窗口、BDP 与丢包下每个分片的 CPU 开销。

**接收内存**：由每个流的接收窗口限制（`rcv_wnd` 个分片，应用不读时通告零窗口），连接内最多 64 个流；`anl_get_stats` 的 `rcv_bytes` 报告各流 rcv_buf/rcv_queue 的载荷合计。

### 6.4 flush 调度顺序

1. 待发 ACK、窗口探测、CTRL（STREAM_OPEN、REPORT 等）、FWD、CLOSE 与 RST；纯控制数据报不消耗 pacing 令牌。
2. 重传：默认流先发，再按优先级从高到低；还有新数据时最多使用可用令牌的 3/4，给新数据留份额。发送状态仅在实际发出时更新。
3. 新数据：默认流严格优先，其余流按优先级 0..3 的每流 DATA 分片额度 8:4:2:1 轮询。pacing 或拥塞窗口中断时保留本轮剩余额度，避免每次 flush 重置额度饿死后面的流；无待发数据或流窗口阻塞的流让出额度。默认流持续占满发送能力时不保证其他流进展；额度也不是线上字节比例。轮到流时先发其到期的 FEC 校验包，再发新数据；二者均受令牌与预算约束。
4. 对没有新数据、仍有到期校验包的流按优先级补发。校验包单独占一个数据报，小块的校验包可搭载在同一流下一块的首发数据之后（8.2）。

处理 ACK 释放发送窗口，或 RACK 发现丢失后，`anl_input` 可立即触发 flush，仍受 pacing 约束。部分分片因令牌不足推迟时不提前修改重传退避或次数。

遍历：流最多 64 个，各步都直接走流链表；按优先级的各轮只处理有发送状态（待发、在途、未封块或待发校验包）且属于该优先级的流。

### 6.5 即时发送与应用时钟

`anl_stream_send_frame` 成功时，`flush_on_send=1` 会立即 flush；半可靠流默认开启、普通可靠流默认关闭，默认流另行开启。所有发送都需要先通过 `anl_update` 初始化协议时钟。

应用传入 32 位单调毫秒时间，内部按有符号差值处理回绕。定时器按 `anl_check` 返回的时刻驱动；每个 `anl_input` 前还要检查当前时间，只要已变化就先 `anl_update`，即使下一个定时器尚未到期。接收批次内也须刷新，并限制批次工作量以保证定时器和应用得到调度。库没有系统时钟，无法自行发现调用方传入过时时间。

### 6.6 连接存活

`dead_link` 默认 20：可靠数据的发送次数或 FWD 的重试计数达到阈值时连接判死；STREAM_OPEN 不计入。可靠数据的超时重传和反复的 RACK 重传都退避（6.3），20 次发送对应几分钟，而不是 20 个往返。计数不是统一的“20 次数据重传”：DATA 的 xmit 包括首次发送，FWD 的检查使用其重试计数。半可靠数据通过期限回收，主要依赖 FWD 的存活判断。

`idle_timeout_ms` 服务端默认 30000，客户端默认关闭；超过该时间没有被连接接纳的认证数据报会判死。`keepalive_ms` 默认关闭；开启后空闲发送零段数据报，始终填充，即使 pad_max 为 0 也加 1..16 字节。建议 keepalive 小于对端 idle timeout 的 1/3。

`anl_state` 返回 0（正常）或 -1（dead）。判死后停止 flush 与新发送；input 仍可处理报文用于诊断。应用负责释放并建立新连接。

### 6.7 发送速率限制（pacing）

带 DATA 或 PARITY 的数据报由连接级令牌桶限制，消耗按实际加密数据报长度计算，含认证标签与填充，不含外层 IP/UDP 头。纯 ACK/CTRL/FWD/keepalive 不消耗令牌。

普通速率为 `pacing_gain × 有效带宽模型`；未有模型时按 `init_cwnd × mss / max(srtt或200ms, interval)` 乘 STARTUP 增益。普通下限为每个模型 RTT 至少 4 个 mss；限速器测试或已确认上限时下限也受测试目标约束。`cfg.pace_rate > 0` 始终作为最终上限。`start_rate` 与应用受限的突发速率约束见 6.8。

桶容量默认 `4 × mtu`；启用 start_rate 且未显式设桶时为 1 个 mtu。空闲积累不超过桶容量；上次因令牌不足而停止时，可容纳至多一个 interval 应得的令牌，避免调用间隔限制吞吐。`anl_check` 返回周期 flush、因令牌不足暂停时下一个包令牌凑齐、keepalive（已设置 output）及 idle timeout 中最早的时刻，即 `anl_update` 真正会动作的时刻；各流的 ACK、封块、校验包、RTO、RACK 等定时都在 flush 中处理，不单独唤醒。实时流建议 1..5 ms 的驱动精度。

没有关闭 BBR 或 pacing 的选项。应用码率超过路径时，半可靠队列由期限/字节上限回收；编码器应参考 `target_rate`，以 `backlog_bytes`、丢帧与接收报告辅助判断。

### 6.8 拥塞控制与带宽估计（BBRv2 / v3）

当前实现采用 BBRv2 的模型与丢包约束思路，PROBE_BW 采用 BBRv3 式四相位；并非标准 BBR 的逐行移植。瓶颈带宽取最近 10 个有效轮次的最大交付速率，min_rtt 使用 10 s 窗口。模型 RTT 至少为 interval，避免极短 RTT 的毫秒量化误差放大速率下限。

普通有效带宽为 `min(btl_bw, bw_lo)`（bw_lo 为 0 时无此约束）；限速器已确认时使用确认速率，上探时使用当前探测速率。`BDP = 有效带宽 × 模型 RTT`，普通 cwnd 约为 `2 × BDP + 3 个分片`，受 inflight_hi、最小窗口和初始/突发余量共同限制。

分片保存发送与交付计数快照；一个数据报处理完生成一次速率样本：交付增量除以发送区间与确认区间的较大者。短于 min_rtt 的采样区间忽略。字节计数按载荷加每段 34 字节估算（`SEG_WIRE_OVH`），另对部分 FEC 校验字节给交付信用；这是模型口径，不等同于抓包的 IP/UDP 实际字节。

无排队样本可补入发送速率信用，最多为交付速率的 1.5 倍；比较时先扣除发送侧校验字节，避免重复补偿 FEC。短 RTT 的非应用受限样本另受至少 10 ms / interval 的交付窗口约束，不高于窗口速率的 9/8。

应用受限样本只在高于当前估计时更新模型，相应轮次不推进最大值滤波。所有发送队列都空、令牌与预算仍有余量时标记应用受限；窗口阻塞不算。容量不足且仍有实际丢失时抑制该标记，有界恢复探测除外。模型长期只有应用受限样本时允许起步增益与初始窗口的突发余量；应用受限样本若带回排队（RTT 超过 min_rtt 的 1.25 倍且至少 5 ms，与排队信号同一阈值），说明突发已填满路径，与非应用受限样本一样在 10 个轮次内取消该余量——否则编码器跟随目标码率、长期应用受限的发送端在长 RTT 下每个关键帧都以 2.9 倍发进瓶颈队列；已测得较快的应用突发还可使用 burst_bw，存在排队或 policer 时不启用该突发加速。

| 状态 | pacing 增益 | 主要退出条件 |
|---|---|---|
| STARTUP | 2.885 | 3 个非应用受限轮次带宽增长不足 25%，或拥塞丢包 |
| DRAIN | 1/2.885 | 在途量降到 BDP |
| PROBE_BW | DOWN 0.9、CRUISE 1、REFILL 1、UP 1.25 | min_rtt 到期时进入 PROBE_RTT |
| PROBE_RTT | 1，窗口约 BDP/2 | 至少 200 ms 且完成一个轮次；应用受限时避免进入 |

DOWN 等队列排到 BDP 后进入 CRUISE；到探测时间进入 REFILL，清 bw_lo，一个轮次后 UP。UP 至少一个 min_rtt 后，在途达到 1.25 BDP、连续两个轮次带宽增长不足 1/8 或发生拥塞时结束；容量恢复允许延长有增长的 UP。常规探测在进入 DOWN 后随机等 2..3 s，或达到 `min(BDP分片数, cwnd, 63)` 个轮次，先到者触发；容量恢复可提前触发。

丢失超过 2% 且上一轮最小 RTT 仍有排队，或 PROBE_BW 丢失超过 50%，才按拥塞处理。通常降低 inflight_hi 和 bw_lo；无排队的随机丢包避免直接压低速率。应用受限、平滑丢失低于 1/8 时，bw_lo 保留本轮实际发送所需的速率，inflight_hi 不被这种样本压低。STARTUP 另有过冲退出：模型已达到初始窗口对应带宽的 4 倍、丢失字节超过 8 个估算分片且一轮丢失超过 40% 时结束起步。RTO 仅在排队或极高平滑丢失时启用一个轮次的包守恒。

路径 RTT 持续变长时，通过多个拥塞轮次中降速与交付同步下降的关系识别传播时延变化，更新 min_rtt 并解除相应旧约束；此外，持续且不随降速变化的平坦 RTT 可触发主动 PROBE_RTT，排空后再确认传播时延；同一传播时延只探测一次，只有 RTT 低于此前任何一次 PROBE_RTT 前后所见的 min_rtt 才重新允许，min_rtt 过期重取、或排空不彻底使 min_rtt 略高，都不算新值；STARTUP 后 8 个轮次内，若非应用受限轮次丢失超过 25%、覆盖至少半窗口且交付速率不足历史峰值一半，会裁去过时带宽峰值。它们是启发式判断，不能保证识别所有路径变化。

**令牌桶限速器检测** 使用四个内部状态：观察、降速测试、已确认限速、逐级上探。检测区间至少 4 个轮次和 300 ms；无排队、显著丢失（非应用受限区间超过 10%，应用受限区间超过 25%：此时交付的就是路径能通过的，随机丢包不会到这个程度）且交付稳定时降速验证。测试区间非应用受限、或至少发出了测试速率的一半时，丢失减半即通过（随机丢包在任何速率下都不会减半）；应用受限且发送不足一半不作结论，只短暂等待。丢失降低后再以基准 1/4 为步长上探，最多 16 步，须看到交付平台与额外丢失才确认上限。变速后的过渡轮次不计样本；上探或其尾段供给不足不作容量结论，以测试通过的速率为上限直到下一次上探（首次确认也如此：媒体流的编码器跟随估计下调，尾段很少喂满）；持续排队交回普通 BBR。区间的送达率取对端报告的 `rx_bytes`（6.9）：两份快照属于当前发送速率阶段、覆盖至少半个区间且足够新时用报告，否则按 ACK 统计。稳定阶段可复用不超过 `max(srtt, 200 ms)` 的旧端点（报告周期是 `max(srtt, 100 ms)`，但只收不发的一端没有 ACK RTT，按 RTO_DEF 即 200 ms 报告）；报告给出的速率不超过同一区间本端发送量的 2 倍（对端只能收到发出去的，2 倍留给报告的滞后）；变速后由 `sender_ts` 确认快照已经见到新阶段，报告长时间缺失后的首份只作为新基线，不能把缺失期的交付用于当前区间。按 ACK 统计时，发送端因帧过期丢掉的已发段之后到达也无法结算，媒体流在限速器后读出的送达率比路径实际通过的低约 22%，测试速率因此锁在限速的三分之二左右。容量不足（`capacity_short`）期间不发起新的限速器确认：帧过期与编码器降速会污染丢失减半的判定，恢复后再观察。应用受限的首次测试供给不足时，可在同一测试速率再等一个区间，仍不足就退出；高于估计上限的上探不延长。首次测试按速率 R 发送且发满（至少 7/8），丢失没有减半而送达低于 R 和实际发送量的 7/8 时，上限在 R 以下（检测区间里令牌桶仍在排空），按该区间的送达率立即重测一次；随机丢包超过 1/8 时重测同样失败，不再重测。

输入间断（超过 RTO 未收到数据报）恢复后 5 s（`LT_GAP_MS`）内结束的检测区间整体丢弃：断网遗留的丢失、放弃的帧和积压重传使首个区间读出 40–60% 丢失，紧随的降速测试只剩路径随机丢失，会被误判为"降速后丢失减半"而确认限速器。

周期上探可恢复更高容量；确认上限仍在时逐步延长间隔，容量明显下降则重新测试。残余随机丢失 ≥20‰ 时可安排低速复核，要求连续两个供给充分、无排队区间才修正补偿；短模型 RTT（<75 ms）的已确认上限上探，需要连续两个检测区间出现排队才撤销限速。上探有时间与步数边界，不能保证识别任意大突发额度的整形器。

**`cfg.start_rate`** 默认为 0（关闭）。开启时从应用给出的预期字节速率起步，扩大初始窗口到约 300 ms 的量；速率上限随后跟随迄今最快交付速率的 9/8，只升不降，仍受 cfg.pace_rate 限制。受该上限约束的样本视作应用受限。提示速率按线路字节理解：按它发送期间，每个带数据的数据报另计 28 字节 IPv4/UDP 头，否则提示接近瓶颈速率时，载荷会略多于线路能承载的量。提示过低会使数据在发送端排队，应用应按媒体、冗余和重传需求配置。

`anl_get_stats` 暴露 bw_estimate（模型估算的字节/秒）、bw_app_limited、最近网络受限样本的 age、min_rtt、cc_state 与当前 pace_rate。尚无网络受限样本时 age 为 `0xffffffff`。bw_estimate 可保留旧峰值，编码器优先使用 target_rate。

### 6.9 接收端时延统计与反馈

每流测量 `transit = 本地时间 − 对端报文时间戳`，以两个 5 s 窗口的最小值作基准。无需同步绝对时钟，但时钟漂移与路径变化仍会影响基准。

- jitter 按到达间隔差以 1/16 平滑；qdelay 为单分片 transit 超过基准的量。
- frame_delay 从最早分片的发送时刻算到整帧进入接收队列，再减基准，包含排队、重传、FEC 与重组。
- 有数据时按 `max(srtt, 100 ms)` 结束区间，报告抖动、平均/最大排队与帧时延、完成帧数、累计跳过操作和净 FEC 重建数。
- `frames_skipped` 是操作数，一次可跨多帧；实际交付缺口看 lost_before，尾部未交付还须由业务统计。
- `rx_bytes` 是接收端整条连接从网络收到的 DATA 与 PARITY 字节（与发送端 `sent_wire` 同一口径：载荷 + SEG_WIRE_OVH），在段到达时累加，不论之后被丢弃、因帧过期或 FWD 跳过而无用，也包括重复到达；FEC 本地重建的不算。报告写出时取当时的值，与数据报的 ts 对应。每条流的报告都带这个连接级计数和 `sender_ts`。后者按发送端本地时钟还原，不要求两端时钟同步。
- 发送端只用对端时间更新的那份报告推进连接级的 `prx_bytes`（相邻两份的 `rx_bytes` 差）和 `prx_ms`（对端 ts 差）；乱序、重复的旧报告和别的流里较旧的报告不推进，丢失的报告由下一份的差值覆盖。限速器检测用它们计算区间的送达率（6.8）；编码器的有效媒体交付（target_rate）仍按 ACK 统计。
- REPORT 不确认、不重传；两种流 report 默认都为 1（可靠流以前为 0：限速器检测需要报告）。发送端只采纳该流对端 ts 更新的报告，重复/旧报告不刷新 age 或回调。
- `anl_stream_get_stats().rx / peer` 提供本端测量和对端最近报告；anl_set_report_callback 在收到报告时同步调用。

报告中的 FEC 计数扣除乱序导致的伪重建，并暂缓最近 200 ms 的重建，规则见 8.6。

### 6.10 码率自适应接口

target_rate 为全部流合计的可用载荷字节/秒，每 200 ms 更新。基础值为有效带宽 × 平滑载荷占比 ×0.9；载荷占比扣除头部、重传与校验开销，至少 50%。尚无带宽/RTT 样本，或首次累计确认载荷尚不足两个 MSS 时 target_rate 可为 0，应用需要自己的起始码率。

首次反馈等待一个常规双数据报 ACK 批次对应的载荷量，同时暂缓初始化发送/交付均值。小音频包可能先于首个媒体批次完成确认；用它的字节数除以整段 RTT，会把初始码率压到极低，再受每秒 25% 的增长限制长期停留在低点。首个关键帧的发送均值与这一稀疏交付均值还会误触发 capacity_short，关闭音频 FEC。该等待只约束首次反馈，BBR、pacing、流优先级和已有反馈后的容量判断继续按原规则工作；少量稀疏数据可能更晚获得首次反馈。

普通上升不超过每秒 25%。应用受限且队列信号低时允许向上试探，但不超过实际首次发送载荷速率的 1.25 倍。排队时延用 srtt 相对最近两个 15 s 窗口最小值计算。

排队超过 `max(rmin/2, 30 ms)` 时，根据本步交付切速；没有实际丢失时允许采用平滑交付下限，避免关键帧集中确认前的稀疏样本造成过度减速。没有可用交付时每步降 15%，保留最小窗口速率。普通排队回升同样限制在 25%/s。

若已经持续交付受限（capacity_short，或平滑交付低于上一步发送速率的 3/4），目标不超过平滑交付载荷的 90%，保留最小窗口下限；排队分支可在该交付上界内恢复，避免从一次稀疏确认的低点长时间爬升。这个条件在更新本步平均值之前判断。

变化达到 5% 时同步调用 rate 回调；回调只能读取统计。target_rate 当前不直接使用对端帧时延，应用可结合 REPORT 做自己的策略。

## 7. 半可靠流（帧模式）

### 7.1 帧号

- `frame_no` 由协议按流自动分配，从 0 开始，每帧加 1，通过 `anl_stream_send_frame` 的出参返回给应用；
- 应用自己的时间戳（如 PTS）请放在负载里；
- 线上只带低 16 位。接收方扩展为 32 位时，**参考值取已收到（含 rcv_buf 中首片）的最大 frame_no**，而不是最近一次交付的帧。这样长时间断网、丢弃了大量帧之后，只要重新收到的帧号与最近看到的帧号相差不超过 32767，扩展仍然正确。

这样设计的好处：接收方看到帧号跳变，就能精确算出丢了几帧，包括发送端还没发出就被丢弃的帧。

### 7.2 发送

`anl_stream_send_frame(s, flags, buf, len, &frame_no)`：

1. 分配 frame_no；
2. 按 mss 切片；首片设置 HAS_FRAME，关键帧再设置 KEY；
3. 记录帧号和入队时间，放入 `snd_queue`；首次发送时才分配 sn。
4. 分片数不能超过 `rcv_wnd`（由打开方决定、两端相同，见 6.1），否则返回 `ANL_ETOOBIG`。**大 I 帧需要相应调大 rcv_wnd。** 半可靠流的 snd_wnd / rcv_wnd 默认均为 512：snd_wnd 若小于一帧的分片数，一帧要跨多个发送窗口，至少多花 1 个 RTT 才能发完；
5. 若 `flush_on_send` 为 1，立即 flush（受 pacing 约束，见 6.7）。

### 7.3 发送端丢帧

每次 `anl_stream_send_frame` 和每次 flush 时都会检查：

| 条件 | 处理 | 配置项 |
|---|---|---|
| 积压字节数（snd_queue + snd_buf 中未确认的部分）超过 `max_bytes` | 丢弃**最老的整帧**，无论它是否已发出 | `max_bytes`，0 表示不限 |
| **尚未完整发出**的帧（仍有分片在 snd_queue）入队超过 `max_age_ms` | 丢弃该帧；若它已有分片发出，同时放弃所有更老的帧并发 FWD | `max_age_ms`，0 表示不限 |
| **已完整发出**的帧超过 `max_age_ms` | 不丢弃、不发 FWD；正常确认则结束。若它的某个分片需要重传（RTO 超时或快速重传触发），**不再重传**，改为放弃该帧及所有更老的帧并发 FWD | 同上 |

`max_age_ms` 的含义因此是"超过这个时间就不值得再发（包括重传）"，而不是"超过这个时间还没被确认就丢"。已完整发出的帧不会仅因等待 ACK 超龄而主动放弃。

"放弃该帧时一并放弃所有更老的帧"是为了保持被放弃的 sn 为未确认区间的前缀：FWD 的语义是"new_una 之前全部放弃"，若只放弃较新的帧，接收端会把仍在途的较老帧一起跳过。由于帧按入队顺序老化，较老的帧此时也已超龄。

**`drop_until_key`（可选）**：一旦有帧被丢弃，后续非关键帧也一并丢弃，直到出现下一个关键帧：

- 已在队列中的非关键帧：直接丢弃；
- 新提交的非关键帧：返回 `ANL_EDROPPED`，但仍然占用一个 frame_no。应用收到这个返回值后，可以请求编码器立即出一个关键帧。

**丢弃规则**：

- 丢弃始终是整帧；
- 帧还在 `snd_queue` 中时，没有分配 sn，丢弃后不会在序号上留下空洞；
- 帧已有分片分配过 sn 时（无论这些分片还在 snd_buf，还是已被确认移除，只剩尾部在 snd_queue）：
  - 移除它在 snd_buf 和 snd_queue 中的所有分片，停止重传；
  - 必须发 FWD。若只看 snd_buf，"首片已确认、尾部仍在 snd_queue"的帧会被静默丢弃，接收端 rcv_queue 里留下半截帧；
  - `snd_una` 照常取 snd_buf 中最小的 sn（没有时为 `snd_nxt`）；
  - 从丢弃前的 `snd_una` 开始，记录本次移除的已分配序号分片的最大 `sn + 1`；若帧已发出首部、尚有尾部在 `snd_queue`，则取 `snd_nxt`，覆盖这帧已经发出的部分。以此单调推进 FWD 的 `new_una`，并标记 FWD 待发。

不能从剩余发送缓存反推跳过边界：SACK 会移除已确认分片，后续完整帧也可能已经全部从缓存中移除。取“第一个存活帧的首序号”可能越过接收端已经收到的有效帧；取“第一个存活分片”还可能越过有效帧的首片。当前实现只依据被放弃的分片确定边界，不再保存 `first_sn` / `cur_first_sn`。已确认的被放弃帧尾片可能使边界落在帧中间，接收端仍按 7.5 的组帧校验处理残片。

### 7.4 FWD 的可靠性

- 发送端只维护**一个**待发的 `new_una`，多次丢帧时取最大值；
- **新的丢帧立即通告**：上一次 FWD 发出后 `new_una` 又前移时，下一次 flush 就发出带最新值的 FWD，不等重发定时器，也不等上一个 FWD 被确认。这种 FWD 不计重发次数、不改退避，定时重发照旧。对端在空洞上等的正是这条消息：只靠定时器时，每次丢帧后音频要多等一个 RTO 或一个往返，接收端缺席 40 s 后路径恢复的首个音频中位数为 970 ms，改后为 480 ms（RTT 200 ms、10% 丢包，40 个种子）；稳态仿真中准时率与带宽不变（±0.2%）；
- FWD 从 RTO 起按数据分片的规则**退避**重发，直到收到的 ACK 中 `una ≥ new_una`；重发次数计入 dead_link。**收到的 ACK 中 una 有推进时，重发计数与退避间隔清零，并把未来重发期限收敛到至多当前时间加一个 RTO**：持续拥塞下发送端不断丢帧，new_una 一直前移，对端的 una 永远追不上最新值，若不清零，计数会跨越多个 new_una 累加，约 20 个 RTO 后把一条正常的连接判死；
- 接收端收到 FWD 后必须排一个 ACK（5.3），否则在发送端暂时没有新数据时（例如 `drop_until_key` 等待关键帧）FWD 永远得不到确认；
- 如果 ACK 中的 una 落后于发送方的 snd_una，发送方忽略它。
- **退避只在对端无声时起作用**：收到对端的 ACK、其 una 既未推进也未越过 `new_una`（FWD 丢了，或对端在长时间收不到本端之后把窗口外的 DATA 全部丢弃），且距上一次发出 FWD 已超过一个 RTO 时，立即重发 FWD 并把间隔重置为 RTO。配套地，半可靠流的接收端对**窗口外**（sn ≥ rcv_nxt + rcv_wnd）的 DATA 也要排一个 ACK（正常 ACK，带 FRESH）——这种段只可能来自已经放弃了 sn − rcv_wnd 之前全部分片的发送端（发送端不会越过 una + 窗口发送），存不下，但 ACK 让发送端知道对端活着、停在哪里。这样恢复路径上的 ACK 可及时触发 FWD，不必等待已增长的静默退避间隔。

### 7.5 接收端

**收到 FWD(new_una) 时**：

1. 若 `diff(new_una, rcv_nxt) ≤ 0`，忽略该 FWD（但仍排一个 ACK）。FWD 每 RTO 重发一次，乱序或重复到达的旧 FWD、或接收端已经自行跳过的情况下，`rcv_nxt` 决不能倒退；
2. 丢弃 `rcv_buf` 中所有 sn < new_una 的分片；
3. 丢弃 `rcv_queue` 尾部不完整的帧；
4. 令 `rcv_nxt = new_una`；
5. 继续把 rcv_buf 中连续的分片移入 rcv_queue；
6. 排一个 ACK。

**接收端截止时间（`rcv_deadline_ms`）**：半可靠流默认 -1，取接收端本地 `max_age_ms` 的 3/5（`RCV_WAIT_PCT`，默认 500 ms 时为 300 ms，音频常用的 200 ms 时为 120 ms）；0 显式关闭，正数使用独立期限。接收参数不随 OPEN 传递，应用应在 accept 回调设置本地期限。

默认值曾是整个 `max_age_ms`。应用的播放预算通常短于 max_age（发送端多留余量），等满 max_age 时，补不上的缺口会把后面没有丢包的帧也拖过预算。仿真（关闭 FEC，2 Mbit、60..300 ms RTT、3..15% 丢包，3 个种子，音频 / 视频 max_age 200 / 500 ms，按 150 / 300 ms 预算计）比较了 1/2、3/5、2/3、3/4 与整个 max_age：3/5 平均音频 +0.55、视频 +2.6、关键帧 +0.95 个百分点，没有明显变差的场景；1/2 视频最好（+3.4），但 100 ms RTT 时音频变差（3% 丢包 99.4 → 98.9）。开启自动 FEC 时 3/5 与原默认值持平。代价：RTT 很短、两次重传仍赶得上 max_age 时，第二次重传可能被放弃（60 ms RTT、5% 丢包音频收到比例约 −0.2 个百分点）。实网（关闭 FEC，音频 / 视频等待 130 / 250 ms，与本默认相近）见 COMPARISON.md 2.5。

- 触发条件：`rcv_nxt` 处有空洞，且 rcv_buf 中空洞之后已有数据，这种阻塞状态持续超过 `rcv_deadline_ms`。计时从空洞出现时开始，只有 `rcv_nxt` 前进才重新计时；
- 处理方式：接收端主动跳到空洞之后第一个带 HAS_FRAME 的分片，并立即排一个 ACK；
- 跳过之后，ACK 中的 una 前移，含义为“接收方不再需要该 sn 之前的数据”，不能把整个前缀都作为成功交付来增加拥塞控制的 delivered。每次本地期限跳过记录目标帧首片的完整 32 位 sn，作为 `RCV_SKIP.retired_una`；该点之后真正收到的连续分片仍由普通 ACK 确认。
- 有跳过记录时，每个 ACK 段之前附加 **8 字节** RCV_SKIP，标记与该 ACK 必须在同一数据报中，拆分 SACK 时每段都带。后续 ACK 重复这个标记，避免首次跳过 ACK 丢失后，后来的累计确认又把缺失分片算成交付。未发生本地跳过的 ACK 不增加此开销。
- 发送端只接受半可靠流上 `snd_una < retired_una ≤ snd_nxt` 的标记（按 32 位序号差比较），先回收该前缀、减少在途与积压并释放发送窗口，不产生交付速率样本；随后处理同报文的 ACK。已经被 SACK 确认的数据不重复处理；重复、过旧或越过已发送范围的标记不再释放数据。前缀中可能有已收到但 SACK 丢失的分片，这部分未确认交付保守地不记账。
- 当 `rcv_nxt - retired_una ≥ ANL_MAX_WND`（32768）时可停止重复：发送端若仍保留该前缀，就不能发送超过最大窗口的新序号；接收进展到这里证明前缀已被确认或由发送端自行放弃。用完整 32 位标记避免重复标记跨过 24 位半周时的展开歧义。FWD 引发的跳过不创建本地标记，因为发送方已经回收了它放弃的前缀。
- 本地期限从后续数据揭示缺口时计时，按 update/flush 周期检查；不是从发送端生成帧的绝对时间计时，也无法在没有后续帧时推断丢失帧的年龄。
- **补不回来的缺口立即跳过**：用路径 RTT（本端有 min_rtt 时用它，只收数据时用 ECHO 得到的 echo_rtt）估计缺失数据被重传送到时的年龄——对端收到本端的 ACK 才知道缺口，约在数据发出一个 RTT 后重传，再经过半个 RTT 到达，加上发送端的 RACK 窗口（min_rtt/16）与本端 ACK 等待 flush 的一个 interval：`1.5 × RTT + RTT/16 + interval`。超过本端 `max_age_ms` 时，这个缺口已经补不回来（到达时数据已过寿命），等下去只会拖住它后面的帧，于是在下一次检查时直接跳过，不等 `rcv_deadline_ms`；跳过的处理与普通期限跳过相同（RCV_SKIP 等）。最近收到过本流的校验包（FEC_BLOCK_MAX_MS + RTT 内）时不提前跳过，FEC 可能马上重建它；`rcv_deadline_ms = 0`（显式不跳过）或 `max_age_ms = 0` 时不适用。用 min_rtt 而不是 srtt：排队使 srtt 波动，会把重传仍能补上的视频缺口误判为补不回来。
  - 实网（关闭 FEC，约 170 ms RTT，音频 max_age 200 ms、预算 150 ms）中，每个补不回来的丢包把后面约 4 个音频包一起拖过预算，3..5% 丢包时音频准时率只有 75..89%，SRT（到点丢弃）为 95..97%。仿真（2 Mbit，关闭 FEC）：170 ms RTT 音频准时 83/75/68/56% → 96/94/92/89%（3/5/7/10% 丢包，普通队列），280 ms 83/68/54/34% → 97/95/93/90%；60..100 ms 不触发、结果不变；开启 FEC 时差异在种子噪声内（24 个种子复核）。代价与 SRT 相同：补不回来的那个包直接放弃，"收到"比例相应下降。

**`anl_stream_recv_frame` 返回的 `anl_frame_info`**：

| 字段 | 含义 |
|---|---|
| `frame_no` | 32 位帧号，由 16 位线上值扩展得到 |
| `flags` | 是否关键帧（KEY） |
| `lost_before` | 与上一次交付的帧之间丢了几帧，等于 `frame_no - last_frame_no - 1` |

**组帧校验**：交付前检查 rcv_queue 中构成一帧的 `frg + 1` 个分片 sn 连续、frg 逐一递减，且除首片外不带 HAS_FRAME。不满足时丢弃到下一个帧起点，计入 `frames_skipped`，决不把两帧拼接后交付。发送端规则正确时不会触发，这是防御性检查。

可靠流不允许跳过，FWD 和接收端截止时间都只对半可靠流生效。

### 7.6 关键帧与参考帧依赖

视频的非关键帧（P 帧）依赖前面的帧，一旦前面某帧丢失，直到下一个关键帧之前的 P 帧都无法解码。协议在两端各提供一个选项，默认都关闭：

**发送端 `drop_until_key`**：

- 任何一帧被丢弃（超龄、超过 max_bytes、已发帧需重传时超龄）后进入"等待关键帧"状态；
- 丢弃时一并丢弃其后直到下一个关键帧之间的非关键帧，**包括已经发出、仍在 snd_buf 中等待确认的**——它们即使送达也无法解码，继续重传只会浪费带宽；最后只发一个 FWD，new_una 按 7.3 覆盖被放弃的已分配序号分片；首部已发出、尾部仍在 snd_queue 的丢弃帧由 snd_nxt 确定已发送部分的边界；
- 为此每个分片都记录本帧是否关键帧（线上只有首片带 KEY 标志，首片可能已被确认移除）；
- 之后提交的非关键帧返回 `ANL_EDROPPED`（仍占用 frame_no），直到应用提交关键帧。应用据此让编码器立即产生关键帧。

**接收端 `rcv_drop_until_key`**：

- 交付前检查：若下一帧不是关键帧，且它与上一次交付的帧之间有缺口（`frame_no != last_delivered + 1`），则丢弃该帧（包括它已到达的分片），计入 `frames_discarded`，并继续检查下一帧，直到遇到关键帧；
- 被丢弃的帧计入下一个交付帧的 `lost_before`，`frame_no` 连续性与"交付数 + lost_before 之和 = 最后帧号 + 1"的统计关系保持不变；
- 缺口可能来自网络丢失后发送端放弃、接收端 `rcv_deadline` 跳过，或发送端的 FWD，接收端不区分来源。

**关键帧请求不在协议内实现**：接收端何时请求关键帧、发送端如何响应（立即编码、限速、与 GOP 的配合）由应用层决定。应用可以根据 `lost_before`、`frames_discarded` 的变化，或发送端的 `ANL_EDROPPED`，通过自己的控制流（例如一个高优先级的可靠流）传递请求。

B 帧（不被参考的帧，丢失不影响后续解码）不做特殊处理：丢失任何非关键帧都视为参考链中断。

## 8. 流级 FEC（Reed-Solomon）

### 8.1 配置与范围

`fec=0` 关闭，`fec=1` 持续开启，`ANL_FEC_RTT_AUTO=-1` 根据预计修复时间与近期丢失开启。可靠流默认关闭；半可靠流默认条件模式。持续开启时 fec_ratio=1..100 为固定名义比例（默认 25），0 为自适应；条件模式始终用自适应策略。收发两端均须启用 FEC，接收端可在 accept 回调设置。

FEC 只覆盖首次发送的 DATA，不覆盖重传、ACK/FWD/其他 CTRL。校验包不确认、不重传，仍消耗 pacing 与发送预算。条件模式从创建流时保留 FEC 状态及 12 字节 MSS 余量，即使门槛关闭也有缓存与计算成本；显式 fec=0 可避免这些成本。

### 8.2 分块与发送

连续 sn 的首次发送分片组成一个块；满 64 个、首分片发出满块长（下一次 flush 检查）或下一个分片不连续时封块。块长默认 100 ms；自适应冗余在块打开时按 fec_deadline 计算：扣除 srtt/2、上一块校验包的间隔（(m−1)×5 ms）与抖动余量（2 × interval + 4 × rttval）后的剩余时间，至少 100 ms、至多 400 ms。块越长，同一失败目标所需的校验比例越低（5% 丢包、0.1% 失败：k = 9 需 44%，k = 23 需 26%）；预算不足 100 ms 时保持 100 ms，行为与固定块长相同。实网不限速、固定码率下，约 100 ms RTT 在 3%/5% 丢包时正向带宽 −2.6%/−3.8%，约 190 ms RTT −0.6%..−0.8%，音视频与关键帧持平。块可跨多帧，不能将块长理解为恢复时延的绝对上限。

固定比例分配 `m = floor((k × ratio + carry)/100)`，carry 初值 50，余数带入下一块；m 最多 16，可为 0。因此大块/高比例下实际比例会低于名义比例。自适应的下限与预算见 8.5、8.6。

第一个校验包封块后即可发送，后续间隔至少 5 ms；校验包只在 flush 中发出，每次 flush 每流最多一个，实际间隔取决于 flush 时机（周期 flush，或发帧、收包触发的 flush；5 Mbit、100 ms 仿真中视频约 10..14 ms）；每个单独成包，按流优先级参与调度。小块（`k × Lmax <= 2048`，只看大小，不区分音频或视频）的校验包若不超过 512 字节，改为搭载在同一流下一块的首发数据段之后、同一个数据报里，每个数据段带一个（数据报放不下时等下一个）；25 ms 内没有可搭载的数据段则单独发出。搭载的校验包从不与本块成员同包。最近有排队证据（rate_update 的排队信号）或丢失估计不低于 10% 时不搭载：等待下一个数据段的 0..20 ms 叠加排队会使音频迟到，高丢失时需要多个校验包的块每个都要等。实网不限速：纯音频 3..7% 丢包时正向带宽 −9..−14%，低码率视频 −6..−10%，音视频与关键帧持平；线上格式不变（数据报本来可以同时携带数据段和控制段）。令牌或预算不足时等待后续 flush；新块封块前尝试发完旧块校验包。分片的 RACK 等待基准推至该块最后一个校验包的发送时刻。RTO 也从最后一个校验包起算，但最晚只推到重传仍能在 fec_deadline 内被确认的时刻（ts_enq + fec_deadline − srtt/2 − 2 × interval − 4 × rttval），否则不延后：固定块长 100 ms，自适应可到 400 ms，从发送时刻计时的 RTO 会抢在重建的 ACK 之前（100 ms RTT 下约 80% 的超时重传到达时对端已重建）；而 FEC 失败时，及时的超时重传正是让帧按时到达的第二道保护，完全延后时 180 ms RTT、15% 丢包的视频准时率从 98.9% 降到 97.3%，刚好到达截止时刻的重传又会被记为迟到而推高比例。小块（音频）另有一步：首发分片的 RTO 到期时，按块内仍未确认的成员数与校验包数估算重建失败的概率（丢失率按测得值的两倍），不超过小块失败目标的十分之一（万分之一），且最近没有排队证据、没有容量不足时，把这次重传推后一个 srtt，只推一次——重建的 ACK 正在路上。上面的期限早于重建 ACK 能回来的时刻，5 Mbit、100 ms、5% 丢包时 94% 的音频超时重传到达时对端已经有了。实网：约 60 ms RTT 音频重传 −58%、100 ms −11%，纯音频正向带宽 −2.1%/−1.4%，准时率不变。大块（视频）的超时重传同样多半多余（2 Mbit、100..170 ms、3..5% 丢包仿真中 91..96% 到达时对端已重建，约占视频字节的 5%），按发送端此刻掌握的情况判断：块内应答已超时（srtt + 2 × interval + 4 × rttval）的未确认成员与已重传过的成员算作丢失，其余成员和全部校验包算作在途；丢失数不超过 m，且在途部分再丢超过 m − 丢失数的概率（丢失率按测得值的两倍）不超过万分之三时，把重传推到重建 ACK 应到的时刻（最后一个校验包 + 上述应答时间），只推一次。前提是推后的重传仍能在 max_age 之前到达（推后时刻 + srtt/2 + 2 × interval + 4 × rttval）：FEC 万一失败，帧迟到但不丢，不连累 GOP。关键帧在 2 Mbit 上持续造成的排队不作为拒绝的理由（排队证据在这里几乎一直存在，会挡掉 70..98% 的判断），已看到的块内丢失才是相关丢失的证据。评审中曾按小块的办法对全部块推后，2 Mbit、280 ms 视频准时率降约 2 个百分点、冷启动降 3..5 个百分点：那些推后的重传落在 max_age 之后，帧连同 GOP 一起丢失；加上 max_age 条件后这些场景与基线逐字节相同（280 ms 时推后的重传赶不上，不推）。仿真（2 Mbit、固定码率、3..10% 丢包）：100..170 ms 线上带宽 −0.7..−2%，准时率与关键帧不变或略升；280 ms、冷启动与 10 Mbit 闭环不变。

### 8.3 编码与 PARITY 段

GF(2⁸) 使用本原多项式 0x11d，Cauchy 系数 `C(j,i)=1/((64+j) XOR i)`；i 为数据索引，j 为校验索引。每个 DATA 的规范编码为：

```
flags/frg(u8) | [frg_ext(varint)] | [frame(u16)] | plen(u16) | payload
```

不含 sid、sn 或 OPEN body；短数据补零至最长规范长度 Lmax。校验包 j 为各规范编码的有限域线性组合。

```
sid_hdr : 1..4 字节，type=CTRL
subtype : u8 = 0x01
len     : varint = 6 + Lmax
base    : u24，块首 sn
k       : u8，1..64
m       : u8，1..16
j       : u8，0..m-1
payload : Lmax 字节
```

k 个数据分片与 m 个校验包中任意至多 m 个丢失可恢复，前提是接收端拿到足够独立包、块尚未被跳过、缓存仍保留且分配成功。开启 FEC 的流 MSS 减少 ANL_FEC_OVERHEAD=12 字节，使校验段可放入 MTU。

### 8.4 接收恢复

接收端保留最近 128 个分片规范编码与 32 个校验包，按实际长度分配缓存；对端不可能发校验包时不缓存（8.7）。缺 t 个数据、收到同块至少 t 个校验包时，对 Cauchy 子矩阵进行 Gauss-Jordan 求逆，恢复数据并进入正常 DATA 接收路径、生成 ACK。块内 base、k 等参数须匹配。

已被 FWD 或接收端 deadline 越过的 sn 不再恢复；整块过旧则丢弃校验包。先到的校验包等待 DATA，最多保留 max(2×RTO, 200 ms)，缓存满时替换最老项。frg 与规范长度均有边界检查。

### 8.5 自适应冗余

名义比例从 25% 起，范围 10%..100%。由未被 FEC 修复且重传来不及的丢失、对端跳过操作增量和帧时延证据触发调整（帧时延超出排队 3/4 RTT 视为重传补齐；冗余开启时另加 100 ms 的分块等待，否则每次 FEC 修复都被当作重传，100 ms RTT、5% 丢包时比例因 FEC 自己的成功升到上限）；仅本地过期或 RACK 标记不等于一次已证实的 FEC 失败。超过首次发送的 1% 且至少两次失败时比例 ×1.5+5，每 2×srtt+100 ms 最多一次；200 次首次发送无这种失败时 ×0.8。大帧的校验预算不足桶容量一半时不上调（这些丢失可能来自自身拥塞，比例限在 30%）；该限制只在网络受限或有排队信号时生效：应用受限时预算跟随只反映发送量的带宽估计，偏低，丢失也不是自身造成的。

连接另用 FEC 流首次发送、丢失标记/确认与对端净重建报告估算纠错前丢失率；首窗 50 个包，后续 200 个，前三窗较高值可直接替换，之后按 1/4 平滑。RACK 标记可以参与估算，但撤销伪丢失，不作为 8.6 的硬证据；对端不报告时仍有偏低或乱序带来的不确定性。对端报告重建时，被块覆盖的分片的 RTO 重传被确认后不再计入估算（仍作为硬证据）：重建已在报告里，而 RTO 多半抢在重建的 ACK 之前，同一个丢失会算两次；仿真中 3% 丢包估成 3.3..3.6%、15% 估成约 19%，修正后与实际一致，线上带宽 −2.2..+0.2%，准时率不变。

当重传赶不上 fec_deadline 时，按连接丢失估计计算二项式尾概率下限：普通大块失败目标 1%，小块或有关键帧依赖的流 0.1%；有关键帧依赖的流中，非关键帧大块在一次重传仍能赶上截止时间时（fec_repair_ms 不含第二次重传的预留）也用 1%，FEC 修不了的由及时的超时重传补齐。小块（`k × Lmax <= 2048`）在丢失估计稳定前（前三个估计窗口）采用复制级下限，之后只用 0.1% 的二项式下限：1..3% 随机丢包时音频冗余约 33% 而非 100%；突发丢包下这低估了需要的冗余。大块另受预算限制。最多 16 个校验包使这些概率目标不一定可达，不是实际网络上的保证。

校验包不被独立确认，交付模型只对超出约 25% 的校验字节按丢失估计折算信用；发送侧比较扣除校验字节，避免重复补偿。`anl_stream_get_stats().fec_ratio` 是名义包比例，不是实际线上字节比例或上限；条件门槛关闭时为 0，关键帧仍可能获得单独保护。

### 8.6 RTT 条件、冗余预算与容量恢复

预计修复时间为帧在当前 pacing 下的发送时间 +1.5×srtt +RACK 乱序窗口 +interval；普通帧大小以非关键帧平均长度估算。RTT-auto 的大帧（> 256 字节）另估计重复丢失风险：设 `n = ceil(帧长度 / 流 MSS)`、`p` 为已测连接丢失率，`n × p²` 超过校验下限的失败目标（普通流 1%，drop_until_key 流的关键帧 0.1%）时，再加 `srtt + RACK 乱序窗口 + interval`，为第二次重传留一轮时间。drop_until_key 流的非关键帧在第二次重传仍赶得上 max_age 时用 1%：这时帧只会迟到、不会丢，GOP 不受影响；按 0.1% 时约 100 ms RTT 的非关键帧在 3..5% 丢包下一直带校验包。仿真（2 Mbit、令牌桶、固定码率，3 个种子）：100 ms RTT 3%/5% 丢包线上带宽 −8.1%/−10.6%，150 ms −6.1%/−6.8%，视频准时率变化不超过 0.05 个百分点、关键帧不变，视频 p95 +12..+15 ms；7% 以上 `n × p²` 超过 1%，与原来相同。它只覆盖第一次重复丢失，不保证任意多次或相关突发丢失的尾部概率；音频小帧与显式 FEC 模式只算一次修复。默认 fec_deadline_ms=0 时半可靠流采用 max_age_ms/2；无限寿命且未给独立期限时没有此目标。

**latency_rtt（时延换带宽）**：fec_deadline 是"重传能在多长时间内补上就不需要 FEC"，默认 max_age/2 是固定毫秒数。长 RTT 下它连一次重传都容不下（280 ms RTT 时一次重传约 1.5 × 280 ms），只能靠校验包，带宽代价是视频字节的 35..45%。SRT 的做法相反：不预先发冗余，固定把每个包晚交付一个"延迟"，并建议这个延迟取 3..4 × RTT，丢包全靠重传补。`latency_rtt = N`（1..16，半可靠流，默认 0 关闭）让应用表达同样的取舍：应用能为一帧等 N 个往返，fec_deadline 随之提高到 max(配置值, N × min_rtt)，最多到 max_age（发送端在那里放弃这帧）。min_rtt 是窗口最小 RTT，代表路径而不是本流自己造成的排队；每次 flush 遍历流时更新，门槛、分块长度、RTO 期限与 fec_one_retry 都用更新后的值。只改变发送端何时需要 FEC，不改变交付方式：接收端仍收到即交付，丢失由重传补上的帧才会晚到。应用需同时把 max_age 放宽到 N × RTT 以上，否则被 max_age 截住（500 ms 时约 250 ms RTT 以上一次重传就放不下）。

仿真（2 Mbit、固定 1 Mbit 视频、3..10% 丢包，应用的视频预算 L = max(300 ms, N × RTT)、max_age = L + 200 ms，按 L 计准时）：N = 4 时视频基本不再发校验包，线上带宽 −17..−25%（100..280 ms，令牌桶）、−10..−22%（普通队列），视频按 L 准时 99.5..100%（默认配置下 280 ms 普通队列只有 76..95%，因为 300 ms 预算容不下重传），代价是有丢失时延迟上升：280 ms RTT 时视频中位额外时延 120..300 ms、p99 530..1000 ms。N = 3 时带宽 −4..−23%，中位时延增加较少。100 ms RTT 下 N = 3 等于 300 ms，比默认的 250 ms 只宽一点，带宽 −5..−9%。

**门槛**：大帧在 repair>deadline、连接已测丢失≥1%、最近 30 s 有硬丢失证据时开启；repair<3/4 deadline，或至少两个估计窗后丢失<0.25% 时关闭。小帧（平均≤256 字节）按修复时间与近期硬证据开启，不因丢失估计短暂下降而关闭。硬证据来自真实重传确认、RTO 丢失、带更高 sn 送达证据的过期放弃、对端净重建报告；单独 RACK 标记或晚确认不算。

**有界音频启动保护**：从流首次发送开始，已有 RTT 样本且修复来不及时可先保护，最多 2×srtt、硬上限 1 s。额度永久耗尽，不因时钟回绕续期。额度与近期硬证据都过期时立即关门；其后真实丢失仍可重新开启。普通切换保持至少 2 s，首次硬丢失开启、证据到期关闭、容量不足关闭除外。

**关键帧**：drop_until_key 流中含关键帧的块按关键帧大小单独计算修复时间；尚无丢失估计/硬证据时可按至少 25% 的初始保护生成校验。已有测量后要求近期硬丢失与≥1% 丢失。若已知重传能及时修复则不额外保护。

**伪重建**：接收端记录最近 16 次重建及所用校验时间。原始包随后到达且发送时刻不晚于校验包时，视为乱序造成的伪重建。REPORT 扣除此类重建并暂不计入最近 200 ms 的重建；发送端净计数回退按零增量处理。统计 fec_recovered 仍记录实际执行的重建次数，不等于真实丢包数。

**冗余预算**：每 200 ms 估算 `0.9×有效带宽 − 其余发送速率`，按 1/8 平滑。桶容量为 max(半秒预算, 8×mss)。自适应大块超出约 10% 基础比例的校验包消耗预算；关键帧可透支一个桶，非关键帧大块另受约 30% 包比例限制（按整包向上取整）。小块不受该预算限制，但仍受连接 pacing。RTT-auto 流在最近 15 s（`RATE_RTT_WIN`）内观察到排队（`srtt − rmin > max(rmin/4, 25 ms)`）时，每个大块的校验包另不超过 `预算速率 × 100 ms` 的量，避免把积累的预算集中成一个突发塞进链路队列、挡住后到的高优先级音频；约 10% 的基础比例不受此限制。预算不足时大帧不继续提高名义比例。固定比例不受自适应门槛、此预算或容量不足的禁生成规则限制。

**容量不足 capacity_short**：平滑交付载荷低于发送载荷的一半，或反复出现发送前过期字节，连续 3 个控制步进入；前 1 s 不判断。未发送过期的进入条件还要求两次事件相隔至少 1 s、位于 6 s 内，且平滑过期量超过提供载荷的 1/16，避免一次积压清理被视为持续不足。

容量不足时暂停生成所有自适应校验包（含关键帧）、清预算，门槛立即关闭；此前已经生成的校验包仍可发完。退出后普通门槛至少等待 2 s。普通退出要求交付超过发出的 3/4、未发送过期低于提供载荷的 1/64，连续 10 步，且状态驻留至少 3 s。

仅因未发送过期进入时，连续 5 步无明显丢失与排队也可退出，仍满足 3 s 驻留；连续 3 步平静可提前释放 bw_lo、推进 PROBE_BW，在退出后的短期继续模型恢复。应用受限的压制只在交付低于发出的 15/16 时生效。这里的交付比例含重传与放弃影响，不是网络原始丢包率。

**有残余丢失的有界恢复探测**：进入至少 5 s、连续 5 步无队列/限速器状态、交付超过发送的一半且仍有残余丢失时，尝试恢复原始数据发送。保持 capacity_short=1 与自适应冗余关闭，释放 bw_lo、允许突发余量和应用受限样本。探测期间，码率反馈暂不受旧交付量 ×0.9 的上界限制；普通 25%/s 的上升从不低于实际平滑发送量的位置开始。这样应用已有最低码率时，探测能产生额外负载来验证容量，而不是只提高 pacer、仍让编码器低于原发送量。至少观察 1 s 且平滑交付增长超过 25% 才退出；探测最长 1.5 s，在控制步检查。排队/限速器出现即停止，失败后重新等待至少 5 s。

成功后观察 4 s，避免旧积压立即触发重入；观察中队列/限速器出现立即回退。探测有额外发送代价，限制的是时长，不是相对真实容量的超发字节数；实际恢复时间与质量取决于路径和负载，历史数据见 PERFORMANCE.md。

### 8.7 缓存占用

FEC 的内存几乎全在两处：发送端当前块的规范编码副本（最多 64 个分片）与校验包（最多 16 个），接收端最近 128 个分片与 32 个校验包的副本。缓冲按用到的最大长度保留，2 Mbit 视频时发送端约 76 KB、接收端约 178 KB，而自动模式多数时间门是关着的，这些副本白占着。现在只在可能用到时才收集，不用时释放（数组本身留着，再用时重新分配）：

- **发送端**：一个块开始时判断它能否得到校验包。固定比例或不带 RTT 门的自适应总是收集；RTT 门（默认）在门开着、音频起步、尚无任何丢失信息（第一个关键帧）时收集；否则要求最近 30 s（`FEC_LOSS_RECENT_MS`）有硬证据的丢失（开门与关键帧单独开门都要求它），并且这一帧是 drop_until_key 流的关键帧，或典型帧的修复时间超过 `fec_deadline` 的一半。门在块结束时按当时的 RTT 判断，关键帧自己造成的排队会在帧内把 RTT 抬高（2 Mbit、20 ms：修复时间 192 → 226 ms），所以留了余量，关键帧不看修复时间。不收集的块不做副本，已有的缓冲在校验包发完后释放。重新收集的第一个块就是可能开门的那个块。
- **接收端**：流的前 30 s、最近 30 s 内收到过校验包、或本连接任一流最近 30 s 内出现过缺口（对端开门要以丢失为前提，接收端先看到缺口）时缓存；否则不缓存并释放。无丢包的路径两端都释放；有丢包但 RTT 短、门一直关着的路径，发送端释放，接收端仍保留（它不知道对端的期限）。
- 效果（2 Mbit 视频加 64 kbit 音频，仿真）：无丢包时两端从约 270 KB 降到 0（接收端 30 s 后）；25 ms 单向、3% 丢包时发送端 79 KB → 0，接收端不变；150 ms 单向、5% 丢包（门打开）不变。与改动前在 2 / 5 Mbit、20..300 ms RTT、0..15% 丢包、每格 10 个种子成对比较：音频、视频、关键帧准时率之差 −0.007 / −0.048 / +0.115 个百分点（95% 区间 ±0.017 / ±0.075 / ±0.214），线上字节 −0.29%（±0.18，关键帧的块从关键帧开始，不再带上前面的 P 帧）；媒体门槛 24/24。

## 9. 可靠流

语义与 ikcp 相同：

- `anl_send` / `anl_recv` / `anl_peeksize` / `anl_waitsnd`；
- 通过 `opt.stream` 在字节流模式和消息模式之间切换；
- **消息模式下的分片数检查**：一条消息的分片数不能超过 `rcv_wnd`（两端相同），否则 `anl_stream_send` 返回 `ANL_ETOOBIG`。接收方必须凑齐整条消息才能交付，分片数超过它的接收窗口时永远凑不齐，rcv_buf 也无法排出，双方死锁。ikcp 有同样的检查（`count >= rcv_wnd`），接收端必须能在窗口内凑齐整条消息；
- 丢包判定用 RACK（始终启用，6.3），没有 ikcp 的 `nodelay` / `resend`；
- 在可靠流上调用帧接口，或在半可靠流上调用 `anl_stream_send` / `anl_stream_recv`，都返回 `ANL_EMODE`。

## 11. 实现边界

协议库负责连接内的传输；socket、地址管理、PSK 分发与轮换、conv 分配、服务器建连策略、线程调度和业务帧生成由应用负责。没有握手、密钥交换、前向保密、路径 MTU 自动探测或地址迁移验证。

只保证可靠流有序交付；半可靠流可按期限/积压/关键帧依赖放弃，业务必须处理缺帧。默认流是字节流，控制消息应自行分帧。FEC、带宽估计与 target_rate 是有条件的恢复和控制策略，不能保证任意网络下的及时率或吞吐。

性能结论必须绑定测试条件与代码版本，见 PERFORMANCE.md；当前规则以本文件及 anliu.h/c 为准。
