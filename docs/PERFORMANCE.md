# AnLiu 性能测试报告

本报告记录 AnLiu 发布候选版本（提交 `11e4589`）在真实网络上的性能测量：30 轮可靠流、276 条音视频通道，每轮正式统计 600 秒，测试时间 2026-10-10 15:55 至 2026-10-11 03:01（北京时间）。之后在合入发布前清理的 `e9cc568` 上补测了版本回归与 4–20 Mbps 高码率音视频（2026-10-11），单列在第 7 节。不含本机仿真数值。

## 1. 测试总结

- **可靠流**：0.8 / 2 / 5 / 10 Mbps 限速下有效吞吐为限速的 90.6–93.8%，重传 0–49 kbps；不限速时达到主机出口上限（约 30 Mbit 出口的路径 27.82–28.15 Mbps，约 11.6 Mbit 出口的节点 C 为 9.34 Mbps）。全部 30 轮逐字节校验 18.66 GB 无错误，最长接收间隔 0.92 秒，≥1 秒的接收中断 0 次。
- **音视频，2 Mbps 及以上或不限速、无人工丢包**（6 条路径，自动 FEC 与关闭 FEC 各一轮）：音频及时率 99.970–100.000%，视频 99.561–100.000%，关键帧 596–600/600，编码器平均比例 99.3–100.0%。自动 FEC 在无丢包时几乎不发校验包（0.0–12.2 kbps）。
- **0.8 Mbps（低于约 1 Mbps 的标称媒体码率）**：编码器降到 50.5–70.3%，及时视频载荷 414–622 kbps；音频及时率 87.067–91.497%，视频 90.689–95.889%，关键帧 549–583/600。额外时延 P95 约 0.2 秒，是瓶颈排队，链路容量不足时以降码率和少量迟到换取连续交付。
- **自动 FEC（库的默认）：交付更快、更稳，带宽按需花费**。自动 FEC 按 RTT 与截止时间决定是否发校验包：
  - **不需要时不花带宽**：无丢包时校验包不超过 12.3 kbps，低 RTT（重传在一个 RTT 内完成）下 15% 丢包也不超过 0.6 kbps；无人工丢包的 30 对里发送码率与关闭 FEC 相差不超过 1.3%（0.8 Mbps 档除外）。
  - **丢包当场恢复，不等重传**：视频额外时延 P95，中 RTT 10–15% 丢包时 122–148 ms 对关闭 FEC 的 199–239 ms；约 185 ms 路径 1–15% 丢包 43–188 ms 对 159–428 ms；约 275 ms 路径 1–10% 丢包 38–137 ms 对 227–357 ms。
  - **长 RTT 下保住音频、关键帧和码率**：所有丢包轮次音频及时率不低于 99.52%（关闭 FEC 在长 RTT 下约等于 1 − 丢包率，15% 时 85.5%）；10% 丢包以内关键帧最低 595/600（关闭 FEC 在约 275 ms、1–3% 丢包时就降到 371/600）；约 275 ms、10–15% 丢包时编码器保持 90.8–99.4%，关闭 FEC 降到 23.1–68.3%。
  - **代价随丢包与 RTT 增加**：中 RTT 1–3% 丢包多用 6–12% 带宽，10–15% 多 34–36%；约 185 ms 路径 1–3% 多 11–29%，10–15% 多 35–48%。

- **低 RTT 下两种设置没有差别**：重传在一个 RTT 内完成，自动 FEC 不发校验包（≤ 0.6 kbps）；到 15% 丢包，视频与关键帧仍全部及时，音频不低于 99.96%。
- **中 RTT**：1–3% 丢包时关闭 FEC 已基本全部及时（音频最低 99.75%），自动 FEC 多用 6–12% 带宽换来音频接近 100%；10–15% 丢包时自动 FEC 保住全部关键帧，代价是多 34–36% 带宽。
- **长 RTT 依靠 FEC**：RTT 接近视频 300 ms 预算时，一次重传就会超时。约 275 ms 的路径关闭 FEC 时，1–3% 丢包下关键帧最低 371/600，5% 以上编码器降到 23%；自动 FEC 在 10% 丢包以内视频不低于 98.01%，15% 丢包、约 275 ms 时为 92.0%。约 185 ms 的路径上，自动 FEC 比关闭 FEC 多用 11–29%（1–3% 丢包）至 35–48%（10–15%）的带宽。
- **补测：版本回归**（`e9cc568` 对 `11e4589`，同时同路径成对运行，第 7.1 节）：关闭 FEC 29 对、自动 FEC 28 对、2 Mbit 瓶颈闭环 8 对、流开关 17 轮，差值全部在回归限值以内；第 4–6 节的结果同样适用于 `e9cc568`。
- **补测：高码率**（`e9cc568`，关闭 FEC，音频 64 kbps + 固定码率视频 4 / 8 / 15 / 20 Mbps，第 7.2 节）：无人工丢包时三条路径的音视频与关键帧基本全部及时（一轮遇到路径自身约 1–2% 丢包除外），视频额外时延 P95 2–8 ms，发送码率比媒体码率高 5.6–6.6%；1–3% 丢包时视频及时率不低于 99.83%，唯一迟到或丢失的关键帧是每轮起步时的第一个（发送端还不知道路径速率）。
- **边界**：负载是合成帧（音频 64 kbps，视频标称约 940 kbps、每秒一个关键帧，编码器跟随码率反馈），没有真实编解码；每个场景一轮，没有多种子方差；发往节点 D 的路径在晚高峰自身丢包 6–15%，其音视频轮次在凌晨路径干净时测量（第 2.3 节）。

### 2.4 负载与参数

- **可靠流**：`--test stream --wnd 1024 --verify 1`，连续发送并逐字节校验。
- **音视频**：合成帧负载，音频 50 帧/秒、160 字节/帧（64 kbps），视频 30 帧/秒、每秒一个关键帧、标称约 940 kbps，`--adapt 1` 让编码器跟随 AnLiu 的码率反馈；音频与视频各一个半可靠流，音频优先级 0、视频 1。 同一场景同时运行两条通道：**自动 FEC**（`--fec-rtt-auto 1`，库的默认）与**关闭 FEC**（`--fec-rtt-auto 0`，只靠重传）。
- 共同参数：`--interval 10`、`--init-cwnd 16`、`--rcv-deadline -1`；可靠流种子 72 / 73，音视频主矩阵 72 / 73、丢包矩阵 172 / 173（按路径交替）。每个场景一轮。

### 2.5 限速与丢包

- **限速档**：发送端出口 TBF，`rate=<档位> burst=16k latency=100ms`，只匹配本轮的接收端与端口；不限速档只挂 1 Gbit 的计数 TBF。
- **人工丢包**：在发送端用 tc 在两个方向随机丢弃（数据、校验包、ACK 与控制包都可能丢），丢弃发生在应用之外；每轮记录两个方向实际丢弃的比例。音视频主矩阵不加人工丢包。
- **并行**：每轮占一个独立的 tc 频段与端口。不限速可靠流独占收发两端主机；其他轮次按主机出口预算并行（出口限速减 5 Mbit 的余量），音视频的两条 FEC 通道同时启动。

## 3. 统计口径

| 名称 | 含义 |
| --- | --- |
| 有效吞吐 / P10 | 接收端第一个可靠字节起 600 个一秒桶的有效载荷平均值；P10 为逐秒吞吐的第 10 百分位。单位 Mbps（10⁶ bit/s） |
| 利用率 | 有效吞吐 ÷ 限速档位 |
| 发送（含 IP/UDP） | 交给 UDP 的数据报字节加 IP/UDP 头，含协议开销、重传与校验包 |
| 重传 / 冗余 kbps | 重传分片、FEC 校验分片的编码字节 ÷ 600 秒，不含数据报头 |
| 最长接收间隔 | 可靠流接收端两次收到新数据之间的最长时间 |
| 及时率 | 在预算内收到的帧 ÷ 生成的帧（未收到与迟到都计为不及时）；音频预算额外时延 150 ms，视频 300 ms。额外时延 = 单向时延 − 该流本轮最小单向时延 |
| 关键帧 | 及时收到的关键帧数 / 生成的 600 个 |
| 额外时延 P95 | 收到的帧的额外时延第 95 百分位，只含收到的帧，要和及时率一起读 |
| 编码器平均比例 | 合成视频源按码率反馈缩放帧大小的时间加权平均，100% 为标称码率；不是画质评分 |
| 及时视频 kbps | 及时到达的视频帧载荷 ÷ 600 秒 |
| 实际带宽 | 发送端 TBF 计数的正向字节（含 IP/UDP），600 秒窗口平均 |
| 路径自身丢包 | 发送端发出、接收端未收到的数据报比例，扣除 TBF 队列丢弃与 tc 人工丢弃 |

每轮须通过：服务端就绪、两端启动顺序、ping 有回复、进程正常退出、HEALTH 无错误、源码哈希一致、生成帧集合完整、日志完整取回。未通过的尝试（SSH 中断、两端时钟校验失败）整组重跑，不计入结果。

- **版本与设置**：`e9cc568`，关闭 FEC（`--fec-rtt-auto 0`）。音频 64 kbps；视频固定为标称约 940 kbps 的 4255 / 8511 / 15957 / 21277‰，即 4 / 8 / 15 / 20 Mbps，30 帧/秒、每秒一个关键帧，20 Mbps 时关键帧约 530–745 KB；编码器不跟随码率反馈。视频流的发送窗口为 4096 个分片，以容纳一个关键帧。
- **路径**：节点 A→节点 C（约 1 ms）、节点 B→节点 A（约 100 ms）、节点 A→节点 D（约 185 ms）。不加 TBF，只受主机出口约 30 Mbit 限制；tc 双向丢包 0 / 1 / 3%。
- **预算**：音频 120 ms；视频 L = max(120, 4 × RTT) + 一个关键帧的发送时间（20 / 15 / 8 / 4 Mbps 分别加 250 / 175 / 100 / 50 ms）。帧的额外时延不超过"预算 + 10 ms"计为及时。`max_age` 音频 170 ms、视频 L + 200 ms。
- **轮次**：每格一轮，600 秒，2026-10-11 08:50–14:15。20 Mbps、无人工丢包时另跑一轮 `start_rate` 25 Mbps。
- **所需缓冲**：接收端按固定延迟播放时，让 99.9% 的视频帧可解码所需的最小延迟，从第 10 秒起统计。每帧取它所在 GOP 中到它为止最慢的一帧，所以关键帧慢会拖住整个 GOP。

## 8. 复现

测试工具在 `tools/realnet/`（主机表放在仓库之外，见 `tools/realnet/README.md`）。单轮示例：

```sh
# 音视频，2 Mbps，tc 双向 3% 丢包，关闭 FEC
python3 tools/realnet/multi_round.py <发送端> <接收端> <变体> 172 2000 9930 --loss 3 --tc-loss --fec-off
# 可靠流，不限速
python3 tools/realnet/multi_round.py <发送端> <接收端> <变体> 72 0 9930 --loss 0 --unlimited --stream
```

批量运行用 `tools/realnet/multi_sched_pair.py <任务文件> <日志目录>`，任务文件每行一个 JSON（发送端、接收端、变体、种子、档位、丢包、`fec_off`、`stream` 等，见脚本说明）。原始日志与结果文件为内部留档，未随仓库发布。
